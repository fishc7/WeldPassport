## 1. Миссия

**WeldPassport** — система для отдела главного сварщика и участников сварочного
производства трубопроводов.

> **Сначала производство. Потом архитектура. Потом код.**

Система фиксирует не только исполнительную документацию, но и **фактическое
выполнение** сварочного производства: от кадрового учёта и допуска сварщика до
стыка, контроля, исполнительной документации и закрытия истории.

1. **Производство** — как работает цех, кто принимает решения, что является фактом.
2. **Архитектура** — домены, владельцы данных, границы модулей, ADR.
3. **Код** — реализация принятых решений, без опережения документации.

Центральная сущность производственного контура — **стык** (сварное соединение,
**Joint**). Проектная иерархия и утверждённая РД задают контекст и параметры стыка;
производство и контроль формируют историю исполнения через сварочные операции.

Канон жизненного цикла и инженерной модели стыка —
[[docs/project/ADR-007-joint-lifecycle-and-engineering-model|ADR-007]].

## 2. Архитектурный принцип №0. Сначала архитектурная сессия — потом код

Ни одно фундаментальное архитектурное решение не принимается в процессе написания кода.

Любое решение, которое влияет на архитектуру системы, жизненный цикл данных,
границы доменов, модель данных или ответственность модулей, должно пройти отдельную
**Architecture Session** (журнал — [[docs/project/ARCHITECTURE_SESSIONS|ARCHITECTURE_SESSIONS]]).

Архитектурная сессия проводится в формате:

1. Вопрос.
2. Анализ.
3. Обсуждение.
4. Архитектурное решение.
5. Фиксация решения.
6. Создание ADR.
7. Обновление Конституции.
8. Синхронизация архитектурной документации.
9. Только после этого — реализация в коде.

Фундаментальные архитектурные решения принимаются **сериями архитектурных сессий**.

После **каждой** архитектурной сессии:

1. принимаются решения;
2. создаётся или обновляется ADR;
3. обновляется Конституция;
4. синхронизируется `ARCHITECTURE.md`;
5. обновляется `PROJECT_SUMMARY.md`;
6. только после этого допускается реализация в коде.

**Запрещается:**

- изменять архитектуру во время реализации функционала;
- принимать архитектурные решения «по ходу разработки»;
- менять границы доменов без отдельного ADR;
- менять жизненный цикл сущностей без архитектурной сессии;
- внедрять новую центральную сущность без обновления Конституции.

Любое фундаментальное решение считается принятым **только после его документального
закрепления**.

Чат и переписка — рабочий инструмент. Нормативные источники истины — Конституция,
Architecture Sessions, ADR, каноническая архитектура и утверждённые Task /
Implementation Specification. `PROJECT_STATUS.yaml`, Dashboard, Execution Map, Summary
и Roadmap — ненормативные представления состояния и планов; при конфликте действует
приоритет, установленный [[docs/project/ARCHITECTURE_GOVERNANCE#8. Status/control-документы и приоритет канона|AGF §8]].

## 3. Архитектурный принцип №1. Эксперт предметной области + архитектор

Проектирует не AI самостоятельно.

Архитектура WeldPassport формируется **совместно** (роли — [[docs/project/ARCHITECTURE_GOVERNANCE#4. Роли|AGF §4]]):

- **Chief Domain Expert** — реальные производственные процессы и нормативная экспертиза;
- **Chief AI Architect** — архитектура системы, модели данных, доменная модель;
- **AI Development Team** — реализация только утверждённых решений.

---

## 4. Архитектурный принцип №2. Канонический язык проекта

Любая новая сущность WeldPassport должна **сначала** появиться в
[[docs/project/UBIQUITOUS_LANGUAGE|UBIQUITOUS_LANGUAGE.md]].

Только после официального определения термина допускается:

- принятие архитектурного решения;
- создание ADR;
- проектирование модели данных;
- разработка API;
- написание кода;
- создание пользовательского интерфейса.

**Запрещается:**

- создавать таблицы БД для неописанных терминов;
- разрабатывать API для неутверждённых сущностей;
- использовать разные названия для одного понятия;
- использовать одно название для разных понятий;
- вводить новые бизнес-термины без обновления `UBIQUITOUS_LANGUAGE.md`.

Если участники по-разному понимают термин, проектирование **останавливается** до
уточнения термина.

AI не имеет права самостоятельно вводить новые бизнес-термины без Architecture
Session и обновления `UBIQUITOUS_LANGUAGE.md`.

## 5. Architecture Governance

Управление архитектурой WeldPassport регламентируется **Architecture Governance Framework (AGF)**.

AGF определяет уровни управления (Конституция → Architecture Session → ADR → Canonical
Architecture → Task / Implementation Specification → Implementation Decision → Code →
Review), роли участников и обязательную последовательность изменений. Implementation
Decision не может стоять выше или заменять ADR. Полный текст — в отдельном
документе: [[docs/project/ARCHITECTURE_GOVERNANCE|ARCHITECTURE_GOVERNANCE.md]].

Фундаментальные принципы меняются **только** по цепочке AGF. Конституция остаётся
компактным верхним уровнем; детали процесса — в AGF, журнале сессий и ADR.

Канонические термины предметной области — [[docs/project/UBIQUITOUS_LANGUAGE|UBIQUITOUS_LANGUAGE.md]].
Неутверждённые термины в коде и API не допускаются.

## 6. Архитектурные сессии

Все фундаментальные архитектурные решения принимаются **исключительно** в рамках
**Architecture Session**.

**Architecture Session** — официальный механизм развития архитектуры WeldPassport.
Это **процесс**. **ADR** — **результат** процесса. Это разные сущности.

Журнал сессий — [[docs/project/ARCHITECTURE_SESSIONS|docs/project/ARCHITECTURE_SESSIONS.md]].

Результатом Architecture Session является **один или несколько ADR**.

После завершения сессии **обязательно** выполняется:

1. обновление Конституции (при необходимости);
2. обновление `ARCHITECTURE.md`;
3. обновление `PROJECT_SUMMARY.md`;
4. синхронизация связанной документации;
5. только после этого — реализация в коде.

**Сессия не считается завершённой**, пока решения не зафиксированы, ADR не создан,
Конституция и документация не синхронизированы (см. журнал сессий).

## 7. Архитектурные принципы

### 7.1. Один владелец — одна сущность

Каждая предметная сущность имеет **единственного владельца-домена**. Другие модули
обращаются к ней через сервисы и API, не через прямой доступ к чужим таблицам.

### 7.2. История вместо перезаписи

Факты, допуски, контроль и исправления не удаляются без следа. Исправление =
новая версия или корректирующая запись.

### 7.3. Разделение ролей вокруг стыка

Даже если одно физическое лицо выполняет несколько функций, в системе это
**разные роли и записи**:

- официально допущенный сварщик;
- назначенный сварщик;
- фактический сварщик;
- сварщик в исполнительной документации;
- помощник / звеньевой;
- мастер / прораб, подтвердивший факт;
- сотрудник ПТО, внесший данные.

### 7.4. Допуск — результат правил, не флаг

Решение о допуске сохраняется как проверяемый снимок с основанием, а не как
произвольный boolean в карточке работника.

### 7.5. Модульный монолит

Backend — единое приложение с предметными модулями (`hr`, `welding`, `production`…).
Микросервисы на этапе MVP не применяются. Основная БД — **только PostgreSQL**.

### 7.6. Команды, не универсальный update

Переходы статусов и бизнес-действия оформляются командами (`record-welding`,
`activate-admission`), а не произвольным PATCH всей сущности.

### 7.7. Три модели вокруг стыка

Не смешивать **типы** сущностей, но помнить: Joint — центральный объект, вокруг
которого строится весь производственный процесс:

- **инженерная модель** — Joint, изометрия, ревизия РД (`engineering`);
- **события жизненного цикла** — WeldOperation, Inspection, NDTInspection,
  RepairOperation (`production`, `quality`);
- **документальная модель** — ExecutiveDocumentation как результат фактов (`documents`).

Joint — инженерная сущность из утверждённой РД и **центральный объект производственного
процесса**. Модули `production` и `quality` работают со стыком, фиксируя события
его жизненного цикла. Сварщик — участник операции, не атрибут стыка.
Подробности — [[docs/project/ADR-007-joint-lifecycle-and-engineering-model|ADR-007]].

## 8. Домены и границы ответственности

> Полная матрица владения — [[docs/project/DECISIONS#ADR-006. Матрица владения доменами|ADR-006]].

### Производственная цепочка

```text
ОК → ОГС → СМР → ПТО → ОТК → НК → Закрытие
```

(ОТК и НК — разные домены: приёмка качества и протоколы НК.)

### ОК (отдел кадров)

**Единственный владелец:**

- работников (`hr.workers`);
- кадровых данных;
- подразделений (`hr.departments`);
- должностей (`hr.positions`);
- производственных ролей (`hr.worker_roles`).

ОК **не** владеет сварочными допусками, клеймами, WPS и технологией сварки.

### ОГС (отдел главного сварщика)

**Единственный владелец:**

- технологии сварки;
- WPS и PQR;
- сварочных материалов (в части технологии);
- сварочного оборудования (в части технологии);
- профиля сварщика (`welding.welders`);
- сварочных допусков (`welding.welder_admissions`);
- клейм сварщика (каноническое значение — в профиле сварщика);
- технологических карт;
- нормативной информации по сварке.

**ПТО не принимает технологических решений по сварке.** ПТО оформляет
исполнительную документацию на основе фактов и решений других контуров.

### СМР (строительно-монтажные работы)

Владелец факта выполнения: назначения на работу, подтверждение фактической
сварки, участники операции.

### ПТО (производственно-технический отдел)

Владелец **рабочей документации** (регистрация, комплектование РД) и
**исполнительной документации**. ИД — результат процесса (комплект фактов и
подтверждений по стыку), а не файловый архив; файлы — вложения к элементам комплекта.

ПТО **не** владеет допусками, WPS, PQR, кадрами и **не** принимает технологических
решений по сварке.

Владелец **статуса качества и приёмки**: годен / не годен, дефекты, ремонты,
повторный контроль. Использует результаты НК как входные данные.

### НК (неразрушающий контроль)

Владелец **результатов методов НК и протоколов** (ВИК, РК, УЗК, ПВК, МК).
Не принимает итоговое решение о приёмке стыка — это ОТК.

### МТО (материально-техническое обеспечение)

Владелец **поставок, партий, плавок, сертификатов** и учёта материалов/оборудования.
Технологические требования к материалам задаёт ОГС (WPS); МТО подтверждает факт
наличия и сертификации партии.

### ОТК (отдел технического контроля)

Стык — главный агрегат производственного контура. Технология (ОГС), факт (СМР),
контроль (ОТК/НК), материалы (МТО) и ИД (ПТО) сходятся в истории стыка.

### Закрытие

Формирование полной истории стыка и завершение жизненного цикла.

## 9. Модель работника и сварщика

```text
hr.workers          — физическое лицо / работник (ОК)
hr.worker_roles     — производственная роль, в т.ч. WELDER (ОК)
welding.welders     — профиль сварщика, каноническое клеймо (ОГС)
welding.welder_admissions — допуск по методам, материалам, диапазонам (ОГС)
```

Цепочка оформления сварщика:

1. ОК создаёт работника в `hr.workers`.
2. ОК назначает роль `WELDER` в `hr.worker_roles`.
3. ОГС оформляет профиль в `welding.welders` (клеймо).
4. ОГС выдаёт допуск в `welding.welder_admissions`.

Подробности — [[docs/project/DECISIONS#ADR-004. Стабилизация модели ОГС (welders, admissions, stamp_code)|ADR-004]].

## 10. Жизненный цикл проекта

Два параллельных контура сходятся в производственном цикле:

**Контур 1 — работник и допуск:**

1. Приём и кадровый учёт (ОК)
2. Роли работника (ОК)
3. Оформление сварщика и допуск (ОГС)
4. Готовность к назначению на объект

**Контур 2 — стык и производство:**

1. Проект → титул / установка / блок → объект / участок → линия → изометрия (РД — ПТО)
2. Стык (Joint) из утверждённой РД — инженерная сущность (`engineering`)
3. Назначение на работу (СМР)
4. Сварочные операции и участники, в т.ч. сварщики (`production`)
5. Контроль (ОТК/НК)
6. Исполнительная документация (ПТО)
7. Закрытие

Стык не создаётся из факта сварки. При смене РД старые стыки не удаляются —
получают статус `CANCELLED` или `SUPERSEDED` (ADR-007).

Текущий этап реализации: завершение фундамента **ОК + ОГС** перед переходом к
**production / joints**.
