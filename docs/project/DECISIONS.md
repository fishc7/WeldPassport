## 2026-07-01 — Завершение архитектурной ревизии

**Дата:** 2026-07-01

**Контекст:** завершена независимая архитектурная ревизия проекта; выводы
подтверждены тремя согласованными анализами (ChatGPT, Cursor Agent, Claude).

**Принятые решения:**

- Backend принят как основная архитектура.

- Начинается реализация вертикальных бизнес-сценариев.
- Первый вертикальный сценарий — полный жизненный цикл сварного стыка.
- ETL откладывается.
- Import Pipeline остаётся внутри Backend.
- Cursor используется для реализации.
- Архитектурные решения принимаются только после ревизии.

**Связанные материалы:** `docs/ARCHITECTURE.md` (раздел «Архитектурная веха —
2026-07-01»).

## 2026-07-01 — Изменение стратегии разработки

**Дата:** 2026-07-01

**Контекст:** после независимой архитектурной экспертизы (ChatGPT, Cursor Agent,
Claude) пересмотрен порядок вертикальной реализации. Ранее первым сценарием
предполагался полный жизненный цикл сварного стыка (см. запись «Завершение
архитектурной ревизии» выше).

**Принятые решения:**

- Мы изменяем порядок разработки.
- Первым вертикальным сценарием становится полный жизненный цикл работника.
- Вторым вертикальным сценарием станет полный жизненный цикл сварного стыка.
- Контур допуска является фундаментом производственной системы WeldPassport.
- Это решение не отменяет центральную роль сварного стыка в производственном
  контуре.

**Причина:** контур допуска является фундаментом всей производственной системы
WeldPassport.

**Связанные материалы:** `docs/ARCHITECTURE.md` (подраздел «Приоритет первого
вертикального сценария» в разделе «Архитектурная веха — 2026-07-01»).

## ADR-001. Модель организаций и проектов

Дата: 2026-07-02

Статус: принято

Сводный узел: [[03_База_данных/Модель_организаций_и_проектов|Модель организаций и проектов]] ·
канон: [[docs/ARCHITECTURE#Модель организаций и проектов|Архитектура]].

### Контекст

В WeldPassport необходимо учитывать реальные строительные и сварочные проекты, где
в одном проекте могут участвовать разные организации: заказчик, генподрядчик,
сварочный подрядчик, лаборатория НК, технадзор, проектировщик и другие участники.

Модель «1 фирма = 1 проект» не подходит, потому что она ограничивает систему и не
отражает реальную структуру проекта.

### Решение

В системе используется модель связи «многие ко многим»:

```text
companies ↔ projects
```

Связь реализуется через таблицу:

```text
project_companies
```

Минимальные поля:

```text
project_id
company_id
role
```

Одна организация может участвовать во многих проектах.

Один проект может включать несколько организаций.

Роль организации в проекте фиксируется в поле `role`.

Примеры ролей:

```text
customer              — заказчик
general_contractor    — генподрядчик
welding_contractor    — сварочный подрядчик
ndt_lab               — лаборатория НК
inspection            — технадзор / инспекция
designer              — проектировщик
```

### Последствия

Модель позволяет корректно вести проекты с несколькими участниками.

В дальнейшем все модули WeldPassport должны использовать эту модель при работе с
проектами, организациями, документами, сварщиками, стыками, НК и исполнительной
документацией.

AI-агенты и разработчики не должны создавать реализацию по принципу «1 фирма = 1
проект».

Нельзя ограничивать проект одним полем:

```text
projects.company_id
```

Если нужно указать участников проекта, используется связующая таблица
`project_companies`.


## ADR-002. Двойной учёт фактического и документального сварщика

Дата: 2026-07-03

Статус: принято

Полный текст: [[docs/project/ADR-002-double-welder-accounting|ADR-002-double-welder-accounting.md]].

Сводный узел: [[02_Процессы/Сварочные_операции|Сварочные операции]] ·
[[10_Проектирование_WeldPassport/05_Исполнительная_документация/00_Исполнительная_документация|Исполнительная документация]] ·
канон: [[docs/ARCHITECTURE#6. Ключевые правила модели данных|Архитектура — разделение назначения и факта]].

### Контекст

В реальном производстве фактически сварку может выполнить один сварщик, а в
исполнительной документации указан другой сварщик или другое клеймо. Одно поле
«сварщик» в системе приводит к потере производственной или документальной правды.
WeldPassport обязан разделять факт (СМР), документацию (ПТО) и контроль
расхождений (ОГС, ОТК).

### Решение

Сварочная операция хранит **два независимых учёта**: фактический сварщик и
документальный сварщик (с клеймами). Система не подменяет одного другим; при
расхождении фиксируется `mismatch_status` и запись уходит на проверку.

Рекомендуемые поля: `actual_welder_id`, `actual_stamp_id`, `documented_welder_id`,
`documented_stamp_id`, `fact_confirmed_by_worker_id`,
`documentation_confirmed_by_worker_id`, `mismatch_status`, `mismatch_reason`.

Статусы расхождения: `OK`, `MISMATCH`, `NEEDS_REVIEW`, `APPROVED_EXCEPTION`,
`DOCUMENTATION_ERROR`, `FACT_ERROR`.

### Последствия

Раздельный учёт факта и ИД для стыка; контроль ответственности по ролевой цепочке;
основа для будущей модели `welding.weld_operations`, журналов сварки и закрытия ИД.

Код и миграции БД **не меняются** до отдельной задачи реализации.

## ADR: ОГС → Допуски сварщика v0.1

Дата: 2026-07-03

Статус: принято

Связанный коммит: `5f2da02` — feat: add OGS welder admissions MVP.

### Контекст

Backend v0.1 модуля допусков сварщика от ОГС реализован и запушен. Цель v0.1 —
минимальный рабочий внутренний допуск сварщика от ОГС, а не полная модель
удостоверений, клейм и аттестаций.

### Решение

1. Для v0.1 используется схема БД `welding`.

2. Основная таблица — `welding.welder_admissions`.

3. Структура v0.1 — плоская. Отдельные таблицы `welding.stamps` и
   `welding.certifications` пока не вводятся.

4. Причина: полная модель удостоверений, клейм и аттестаций избыточна для
   первой рабочей версии внутреннего допуска.

5. Связь с кадровым контуром:
   - `hr.workers` не трогаем;
   - `worker_id` ссылается на `hr.workers.id`;
   - `worker_id` имеет тип `Integer`, потому что `hr.workers.id` в текущей БД
     `Integer`.

6. UUID:
   - UUID используется для новой сущности `welding.welder_admissions`;
   - генерация UUID на v0.1 выполняется на уровне приложения.

7. API: `/api/v1/ogs/welder-admissions`.

### Последствия

Перенос на v0.2:

- проверка, что работник имеет роль `WELDER`, перед созданием допуска;
- возможное выделение отдельных сущностей `welding.stamps` и
  `welding.certifications`;
- возможная привязка допуска к `project_id` после появления проектного модуля.
