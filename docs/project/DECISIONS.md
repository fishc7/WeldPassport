## 2026-07-01 — Изменение стратегии разработки

**Дата:** 2026-07-01

Claude) пересмотрен порядок вертикальной реализации. Ранее первым сценарием

  контуре.

**Причина:** контур допуска является фундаментом всей производственной системы
WeldPassport.

## ADR-001. Модель организаций и проектов

Дата: 2026-07-02

Статус: принято

Сводный узел: [[03_База_данных/Модель_организаций_и_проектов|Модель организаций и проектов]] ·
канон: [[docs/ARCHITECTURE#Модель организаций и проектов|Архитектура]].

### Контекст

В WeldPassport необходимо учитывать реальные строительные и сварочные проекты, где
в одном проекте могут участвовать разные организации: заказчик, генподрядчик,
сварочный подрядчик, лаборатория НК, технадзор, проектировщик и другие участники.

Модель «1 фирма = 1 проект» не подходит, потому что она ограничивает систему и не
отражает реальную структуру проекта.

### Решение

В системе используется модель связи «многие ко многим»:

```text
companies ↔ projects
```

Связь реализуется через таблицу:

```text
project_companies
```

Минимальные поля:

```text
project_id
company_id
role
```

Одна организация может участвовать во многих проектах.

Один проект может включать несколько организаций.

Роль организации в проекте фиксируется в поле `role`.

Примеры ролей:

```text
customer              — заказчик
general_contractor    — генподрядчик
welding_contractor    — сварочный подрядчик
ndt_lab               — лаборатория НК
inspection            — технадзор / инспекция
designer              — проектировщик
```

### Последствия

Модель позволяет корректно вести проекты с несколькими участниками.

В дальнейшем все модули WeldPassport должны использовать эту модель при работе с
проектами, организациями, документами, сварщиками, стыками, НК и исполнительной
документацией.

AI-агенты и разработчики не должны создавать реализацию по принципу «1 фирма = 1
проект».

Нельзя ограничивать проект одним полем:

```text
projects.company_id
```

Если нужно указать участников проекта, используется связующая таблица
`project_companies`.

### Где зафиксировано

Каноническое описание модели:

```text
docs/ARCHITECTURE.md
```

Правило для AI-агентов:

```text
AGENTS.md
```

## ADR-002. Двойной учёт фактического и документального сварщика

Дата: 2026-07-03

Статус: принято

Полный текст: [[docs/project/ADR-002-double-welder-accounting|ADR-002-double-welder-accounting.md]].

Сводный узел: [[02_Процессы/Сварочные_операции|Сварочные операции]] ·
[[10_Проектирование_WeldPassport/05_Исполнительная_документация/00_Исполнительная_документация|Исполнительная документация]] ·
канон: [[docs/ARCHITECTURE#6. Ключевые правила модели данных|Архитектура — разделение назначения и факта]].

### Контекст

В реальном производстве фактически сварку может выполнить один сварщик, а в
исполнительной документации указан другой сварщик или другое клеймо. Одно поле
«сварщик» в системе приводит к потере производственной или документальной правды.
WeldPassport обязан разделять факт (СМР), документацию (ПТО) и контроль
расхождений (ОГС, ОТК).

### Решение

Сварочная операция хранит **два независимых учёта**: фактический сварщик и
документальный сварщик (с клеймами). Система не подменяет одного другим; при
расхождении фиксируется `mismatch_status` и запись уходит на проверку.

Рекомендуемые поля: `actual_welder_id`, `actual_stamp_id`, `documented_welder_id`,
`documented_stamp_id`, `fact_confirmed_by_worker_id`,
`documentation_confirmed_by_worker_id`, `mismatch_status`, `mismatch_reason`.

Статусы расхождения: `OK`, `MISMATCH`, `NEEDS_REVIEW`, `APPROVED_EXCEPTION`,
`DOCUMENTATION_ERROR`, `FACT_ERROR`.

### Последствия

Раздельный учёт факта и ИД для стыка; контроль ответственности по ролевой цепочке;
основа для будущей модели `welding.weld_operations`, журналов сварки и закрытия ИД.

Код и миграции БД **не меняются** до отдельной задачи реализации.

```text

docs/ARCHITECTURE.md
```

## ADR: ОГС → Допуски сварщика v0.1

Дата: 2026-07-03

Статус: принято

Связанный коммит: `5f2da02` — feat: add OGS welder admissions MVP.

### Контекст

Backend v0.1 модуля допусков сварщика от ОГС реализован и запушен. Цель v0.1 —
минимальный рабочий внутренний допуск сварщика от ОГС, а не полная модель
удостоверений, клейм и аттестаций.

### Решение

1. Для v0.1 используется схема БД `welding`.

2. Основная таблица — `welding.welder_admissions`.

3. Структура v0.1 — плоская. Отдельные таблицы `welding.stamps` и
   `welding.certifications` пока не вводятся.

4. Причина: полная модель удостоверений, клейм и аттестаций избыточна для
   первой рабочей версии внутреннего допуска.

5. Связь с кадровым контуром:
   - `hr.workers` не трогаем;
   - `worker_id` ссылается на `hr.workers.id`;
   - `worker_id` имеет тип `Integer`, потому что `hr.workers.id` в текущей БД
     `Integer`.

6. UUID:
   - UUID используется для новой сущности `welding.welder_admissions`;
   - генерация UUID на v0.1 выполняется на уровне приложения.

7. API: `/api/v1/ogs/welder-admissions`.

### Последствия

Перенос на v0.2:

- проверка, что работник имеет роль `WELDER`, перед созданием допуска;
- возможное выделение отдельных сущностей `welding.stamps` и
  `welding.certifications`;
- возможная привязка допуска к `project_id` после появления проектного модуля.


## ADR-006. Матрица владения доменами

Дата: 2026-07-06

Статус: принято

Полный текст: [[docs/project/ADR-006-domain-ownership-matrix|ADR-006-domain-ownership-matrix.md]].

### Суть

- Стык — центральная производственная сущность; точка схода доменов.
- WPS, PQR, технология сварки — **только ОГС**; ПТО не принимает технологических решений.

Канон границ доменов для всех последующих модулей (`production`, `quality`, `documents`, `mto`).

## ADR-007. Жизненный цикл стыка и инженерная модель

Дата: 2026-07-06

Статус: принято

Architecture Session: [[docs/project/ARCHITECTURE_SESSIONS#Architecture Session 001|Session 001]]

Полный текст: [[docs/project/ADR-007-joint-lifecycle-and-engineering-model|ADR-007-joint-lifecycle-and-engineering-model.md]].

### Суть

- **Joint** — инженерная сущность из утверждённой РД, **центральный объект
  производственного процесса**; все домены работают относительно конкретного стыка.
- События жизненного цикла Joint: WeldOperation, Inspection, NDTInspection,
  RepairOperation, ExecutiveDocumentation (`production`, `quality`, `documents`).
- Стык рождается из **утверждённой РД**, никогда — из факта выполнения.
- Неизменяемый `joint_id`; `project_joint_no` — бизнес-атрибут, уникален только внутри иерархии.
- Каноническая иерархия: Проект → Титул/Установка/Блок → Объект → Линия → Изометрия → Стык.
- Стыки не удаляются; при смене РД — `CANCELLED` или `SUPERSEDED`; существенное изменение → новый Joint.
- Сварщик — участник **WeldOperation**, не свойство стыка; несколько операций и сварщиков на стыке.
- Три типа сущностей вокруг Joint (инженерная / события жизненного цикла / ИД) —
  без смешения ролей; `production` работает **со стыком**, а не вместо него.

Уточняет ADR-006: создание Joint — `engineering`; события жизненного цикла —
`production`, `quality`, `documents`.

## ADR-008. Каноническая модель предметной области WeldPassport (Session 003)

Дата: 2026-07-08

Статус: принято — закрывает Architecture Session 003 (решения 003-A — 003-AM)

Architecture Session: [[docs/project/ARCHITECTURE_SESSIONS#Architecture Session 003|Session 003]]

[[docs/project/ADR-002-double-welder-accounting|ADR-002]]

Канон: [[docs/ARCHITECTURE#5.1. Каноническое ядро engineering-модели (Session 003)|ARCHITECTURE §5.1]]

### Контекст

Session 002 выявила расхождение между упрощённой иерархией
`Project → Line → Isometric → Joint` и реальными производственными документами.
Session 003 фиксирует каноническую предметную модель engineering-контура для MVP:
как Joint появляется, к чему привязан, как идентифицируется, как классифицируется
и как хранит геометрию и материал.

Код, миграции и API **не меняются** до отдельной задачи реализации.

---

### 003-A. СМР и FOREMAN

**СМР** не является отдельной системной ролью. СМР — производственный контур /
зона ответственности, где выполняются строительно-монтажные и сварочные работы.

Факт выполнения сварки от имени СМР подтверждает работник с ролью **FOREMAN**
(мастер / прораб). Для MVP роль FOREMAN достаточна. Роль `SITE_MANAGER` может
быть добавлена позже для разделения мастера, прораба и начальника участка.

Цепочка ответственности:

```text
ОК → ОГС → СМР → ПТО → ОТК/НК → Закрытие
```

- ОК создаёт работника.
- ОГС допускает сварщика.
- СМР выполняет производство.
- FOREMAN подтверждает факт сварки от имени СМР.
- ПТО оформляет исполнительную документацию.
- ОТК/НК подтверждают качество.
- Закрытие собирает полную историю стыка.

---

### 003-B. Минимальная инженерная привязка Joint

Joint **не может быть создан** без привязки к `Project` и минимальному инженерному
источнику.

Для MVP допускается рабочая инженерная привязка в статусе `draft` на основании
данных СМР: объект, участок, Line, Drawing, Isometric или другой рабочий
инженерный источник. ПТО **не обязано** заранее предоставить подтверждённую
исполнительную структуру, чтобы СМР мог зафиксировать производственный стык.

До закрытия исполнительной документации инженерная привязка Joint должна быть
проверена, уточнена и подтверждена уполномоченной ролью:

- **ПТО** — для целей исполнительной документации;
- **ОГС** — для целей сварочного производства, технологии сварки, допуска сварщика
  и корректного учёта стыка.

Минимальные статусы инженерной привязки:

| Статус | Значение |
|--------|----------|
| `draft` | рабочая инженерная привязка |
| `confirmed` | подтверждённая инженерная привязка |

---

### 003-C. EngineeringDocument

В MVP минимальным инженерным источником для создания Joint является универсальная
сущность **EngineeringDocument**.

`EngineeringDocument` хранит рабочий или подтверждённый инженерный источник.
Типы документа (`document_type`):

```text
isometric
drawing
line_list
isometric_register
joint_register
weld_map
field_sketch
repair_scheme
as_built_markup
other_engineering_doc
```

Joint должен быть связан минимум с `Project` и `EngineeringDocument`.
Joint **не создаётся** напрямую «в проекте» — только через инженерное основание.

---

### 003-D. Line как отдельная сущность

**Line** — самостоятельная инженерная сущность WeldPassport. Line **не хранится**
только как текстовое поле в `EngineeringDocument`.

Line создаётся на основании инженерных документов: List of pipelines, Перечень
трубопроводов, Экспликация трубопроводов, Line List, Piping Line List и аналогов.

Line содержит инженерные и нормативные параметры трубопровода:

```text
line_number, материал, среда, DN, давление, температура, категория,
класс трубопровода, процент НК, PMI, термообработка, МКК, изоляция, статус
```

Joint должен быть связан с `Line`, если стык относится к трубопроводу.

---

### 003-E. Isometric как EngineeringDocument

**Isometric** не вводится как отдельная корневая сущность в MVP. Isometric хранится
как `EngineeringDocument` с `document_type = isometric`.

Связь между `EngineeringDocument` и `Line` — через связующую сущность
**EngineeringDocumentLine** (не one-to-one): одна изометрия обычно относится к одной
Line, но иногда — к нескольким.

Правила:

- `EngineeringDocument` может быть связан с одной или несколькими `Line`;
- Joint **всегда** имеет конкретную `Line`;
- если документ связан с несколькими Line, пользователь обязан выбрать Line для Joint.

---

### 003-F. DocumentationPackage

Вводится сущность **DocumentationPackage** — объект учёта передачи документации.
Пакет **не означает** обязательный полный комплект.

В пакет может входить: один документ, несколько документов, полный или частичный
комплект, документ без последующего полного комплекта.

`EngineeringDocument` может существовать:

1. самостоятельно;
2. внутри частичного пакета;
3. внутри полного пакета;
4. сначала самостоятельно, затем быть привязанным к пакету.

Пакет не заменяет `EngineeringDocument` — пакет объединяет документы.

Статусы пакета: `received`, `in_work`, `superseded`, `cancelled`.

Статус полноты: `partial`, `complete`, `unknown`.

---

### 003-G. Источник создания Joint

Joint может создаваться **не только** из Isometric. Joint создаётся из любого
`EngineeringDocument`, если документ связан с `Line` и содержит достаточную
информацию для идентификации стыка или рабочего участка.

Isometric — основной, но **не единственный** источник Joint.

**Может создавать Joint:** `isometric`, `joint_register`, `weld_map`, `field_sketch`,
`repair_scheme`, `as_built_markup`, монтажный чертёж со стыками / участками.

**Обычно не создаёт Joint напрямую:** `line_list`, перечень трубопроводов,
экспликация трубопроводов, `isometric_register` — они создают или уточняют
`Line`, `EngineeringDocument` и документационный контекст.

---

### 003-H. Один основной EngineeringDocument для Joint

Joint имеет один основной `source_engineering_document_id` — главное инженерное
основание, по которому Joint был создан или идентифицирован.

Дополнительные документы участвуют в проверке, уточнении, исполнительном оформлении
или истории изменений, но **не являются** равноправными основными источниками.

---

### 003-I. Уникальность JointNumber

`joint_number` **может повторяться** — номер стыка не является глобально уникальным.

Уникальность Joint в MVP определяется составным контекстом:

```text
UNIQUE(project_id, line_id, source_engineering_document_id, joint_number)
```

**Запрещено:**

- уникальность только по `joint_number`;
- уникальность только по `line_id + joint_number`.

Уточняет правило `project_joint_no` из ADR-007: бизнес-номер уникален в составе
проекта, линии и инженерного основания.

---

### 003-J. Многоуровневая классификация типа соединения Joint

Тип соединения Joint — **многоуровневый**; нельзя хранить всё в одном плоском enum.

1. **WeldShapeType** — геометрический тип: С (стыковой), У (угловой), Т (тавровый),
   Н (нахлёсточный), П (прорезной).
2. **WeldJointDesignType** — нормативное / конструктивное обозначение: С1, С2, С17,
   У1, Т3, Н4 и др. по ГОСТ или проекту.
3. **ProjectJointType** — проектное, международное или заказное обозначение:
   BW, SW, FW и др.

BW / SW / FW не являются ошибкой — хранятся как `ProjectJointType` или alias,
связываются с нормативным типом через правила нормализации.

Нормативные источники: ГОСТ 16037-80 (трубопроводы), ГОСТ 5264-80
(нетрубопроводные ручные дуговые соединения).

Сущность **WeldJointTypeAlias:**

```text
source_text, normalized_shape_type, normalized_design_type,
project_joint_type, mapping_status
```

Статусы сопоставления: `mapped`, `requires_review`, `project_specific`, `unknown`.

---

### 003-K. Геометрия и материал Joint

Joint хранит собственные значения:

```text
diameter_dn, diameter_outer, thickness, material_id,
material_text_source, size_text_source
```

Диаметр, толщина и материал могут подтягиваться из спецификации изометрии / чертежа,
номенклатуры, Line List, ведомости стыков, ручного уточнения ОГС / ПТО — но после
создания являются **атрибутами самого Joint**.

`Line` даёт общий инженерный контекст трубопровода; Joint — конкретные параметры
соединения.

---

### 003-L. Материалы Joint

Joint хранит материал как нормализованную ссылку на **Material**. `Material` связан
с **MaterialGroup** (сварочная / аттестационная группа: М01, М02, М03, М04, М05,
М11, М21, М31, М32, М33, М41, М51 и др.).

`MaterialGroup` используется для ОГС, WPS, допуска сварщика, проверки технологии,
отчётности. Исходное текстовое значение из документа сохраняется отдельно.

Если материал не распознан при импорте — сохраняется как `source_text`, статус
`requires_mapping_review`; ОГС нормализует вручную.

Минимальные сущности:

**MaterialGroup:** `code`, `name`, `description`, `material_class`, `source`

**Material:** `code`, `name`, `group_id`, `standard`, `is_active`, `source`

**MaterialAlias:** `source_text`, `material_id`, `confidence`, `status`

Связь с допусками: `WelderAdmission.allowed_material_groups` проверяется против
`Joint.material_id → Material → MaterialGroup`.

---

### 003-M. Один Joint может иметь несколько WeldOperation

Один `Joint` может иметь несколько `WeldOperation`.

`Joint` — инженерно-производственная сущность стыка, объект учёта.  
`WeldOperation` — производственное событие выполнения сварки над Joint.

`Joint ≠ WeldOperation`.

На один Joint могут приходиться: первичная сварка, корень, заполнение, облицовка,
комбинированный процесс RAD + RD, ремонтная заварка, повторная заварка после
дефекта, сварка после вырезки / переварки.

---

### 003-N. Комбинированная сварка RAD + RD

Для комбинированной сварки RAD + RD используется модель нескольких `WeldOperation`
на один Joint.

Корень, заполнение и облицовка фиксируются как отдельные события, если различаются
по способу сварки, сварщику, клейму, дате, WPS или технологическому этапу.

RAD + RD может отображаться как комбинированный способ в UI, но внутри модели
раскладывается на отдельные операции.

Пример:

```text
Joint W-001
- WeldOperation #1: layer_type = root, welding_process = RAD
- WeldOperation #2: layer_type = fill_cap, welding_process = RD
```

Минимальные `layer_type` для MVP: `root`, `fill_cap`, `repair`.

---

### 003-O. WPS при фиксации WeldOperation

`WeldOperation` может быть создана СМР без подтверждённой WPS/технологической карты
на этапе первичной фиксации факта.

На старте WPS может быть:

- не указана;
- указана предварительно;
- указана как предполагаемая;
- добавлена позже ОГС.

СМР фиксирует факт. ОГС подтверждает технологическую корректность.

WPS не обязательна для фиксации факта `WeldOperation`, но технологическое
подтверждение обязательно для закрытия Joint, исполнительной документации и
финального паспорта соединения.

Минимальные статусы WPS: `not_assigned`, `proposed`, `assigned`, `approved`, `rejected`.

Минимальные статусы технологической проверки ОГС:
`pending`, `approved`, `rejected`, `requires_fix`.

---

### 003-P. Факт сварки, выработка, брак и проверка допуска

СМР может фиксировать факт сварки без мгновенной проверки допуска сварщика.
Такая `WeldOperation` используется для производственного учёта, выработки,
статистики брака и отчётности.

Факт сварки нельзя терять или блокировать, но факт сварки не равен технологически
подтверждённой сварке.

Если допуск/WPS/проектные требования ещё не проверены, операция получает статус
проверки `requires_ogs_review`.

Без проверки ОГС `WeldOperation` не используется для финального закрытия Joint,
исполнительной документации и паспорта сварного соединения.

Разделяются четыре уровня проверки:

1. внутренний допуск ОГС;
2. аттестация/удостоверение сварщика;
3. допуск заказчика на проект;
4. соответствие конкретному Joint (материал, способ, диаметр, толщина, тип).

---

### 003-Q. Defect и журнал ремонта

При выявлении брака создаётся отдельная сущность `Defect`.

Журнал ремонта фиксирует не сам факт брака, а действия по устранению дефекта через
`RepairOperation`, которая должна ссылаться на `Defect`.

Источник истины:

- `Defect` — что обнаружено;
- `RepairOperation` — что сделано для устранения;
- `Inspection` / `NDTInspection` — контроль до и после ремонта.

---

### 003-R. RepairOperation и ремонтная WeldOperation

Ремонт дефекта фиксируется отдельной сущностью `RepairOperation`.

Если ремонт включает сварку, внутри `RepairOperation` создаётся отдельная
`WeldOperation` с `operation_type = repair`.

`RepairOperation ≠ WeldOperation`.

`RepairOperation` отвечает за контекст ремонта (какой дефект, каким способом, с
каким результатом), `WeldOperation` — за сварочную часть (кто, чем, когда, каким
клеймом).

---

### 003-S. Inspection и NDTInspection

Контроль качества разделяется на общий `Inspection` и специализированный
`NDTInspection`.

- `Inspection` — событие контроля;
- `NDTInspection` — детализация НК;
- `Defect` — обнаруженный брак.

Повторный контроль после ремонта фиксируется как новый `Inspection`/`NDTInspection`.

Примеры `inspection_type`: `visual`, `ndt`, `pmi`, `hardness`, `operational`, `acceptance`.

Примеры `ndt_method`: `RT`, `UT`, `PT`, `MT`, `VT` (если проект относит ВИК к НК).

---

### 003-T. HeatTreatmentOperation

Термообработка фиксируется как отдельная сущность `HeatTreatmentOperation`.

Это производственно-технологическое событие жизненного цикла Joint; оно не является
видом `Inspection`.

Журнал термообработки строится на основании `HeatTreatmentOperation`.

---

### 003-U. HeatTreatmentOperation может включать несколько Joint

Одна `HeatTreatmentOperation` может быть связана с одним или несколькими Joint.

Одна диаграмма/цикл термообработки может относиться к группе стыков.
Связь реализуется через `HeatTreatmentOperationJoint`.

---

### 003-V. Один Joint может иметь несколько HeatTreatmentOperation

Один Joint может участвовать в нескольких `HeatTreatmentOperation`
(после ремонта, после неудовлетворительной твёрдости, при отклонении режима и др.).

Причина повторной термообработки фиксируется явно в `reason`:
`initial_required`, `after_repair`, `hardness_failed`, `mode_deviation`,
`customer_requirement`, `ogs_decision`, `other`.

Допускаются ссылки:

- `previous_heat_treatment_operation_id` (nullable),
- `triggered_by_inspection_id` (nullable),
- `triggered_by_repair_operation_id` (nullable).

---

### 003-W. HardnessInspection

Замер твёрдости — вид `Inspection` с отдельной детализацией в сущности
`HardnessInspection`.

Минимальные поля:

```text
inspection_id
heat_treatment_operation_id (nullable)
method
unit (HB / HRC / HV)
measured_value
acceptance_limit_min
acceptance_limit_max
result
conclusion
```

Позже может быть добавлена сущность `HardnessMeasurementPoint` для точек измерения
(`weld` / `haz` / `base_metal`).

Неудовлетворительный `HardnessInspection` может быть основанием для повторной
`HeatTreatmentOperation`.

---

### 003-X. Общий механизм файлов: DocumentFile + Attachment

В системе используется общий механизм файлов:

- `DocumentFile` — описание файла;
- `Attachment` — привязка файла к конкретной бизнес-сущности.

Отдельные поля `*_file_id` в каждой сущности не используются.

Примеры связей: изометрия → `EngineeringDocument`, заключение РК → `NDTInspection`,
диаграмма ТО → `HeatTreatmentOperation`, протокол твёрдости → `HardnessInspection`,
фото дефекта → `Defect`, акт ремонта → `RepairOperation`, WPS → `WPS`,
скан допуска → `WelderAdmission/Certification`, исполнительный PDF → `DocumentationPackage`.

Роли вложений: `source_document`, `report`, `diagram`, `photo`, `scan`, `act`,
`certificate`, `wps_document`, `as_built`, `other`.

---

### 003-Y. Статусы Joint разделяются по контурам

Один универсальный статус для Joint не используется.

Для MVP вводятся отдельные контуры статусов:

- `production_status`;
- `ogs_review_status`;
- `inspection_status`;
- `repair_status`;
- `heat_treatment_status`;
- `documentation_status`;
- `closure_status`.

Примеры:

- `production_status`: `not_started`, `in_progress`, `welded`, `foreman_confirmed`, `cancelled`;
- `ogs_review_status`: `not_required`, `requires_review`, `approved`, `rejected`, `requires_fix`;
- `inspection_status`: `not_required`, `pending`, `in_progress`, `accepted`, `defect_found`, `reinspection_required`;
- `repair_status`: `not_required`, `open_defect`, `repair_in_progress`, `repaired`, `closed`;
- `heat_treatment_status`: `not_required`, `required`, `planned`, `completed`, `accepted`, `rejected`, `repeat_required`;
- `documentation_status`: `not_started`, `in_progress`, `ready_for_review`, `accepted`, `returned_for_fix`;
- `closure_status`: `open`, `blocked`, `ready_to_close`, `closed`.

---

### 003-Z. Финальное закрытие Joint

Финальное закрытие подтверждает отдельная роль `CLOSURE_RESPONSIBLE`.

Роль не заменяет ПТО, ОТК, НК, ОГС или СМР; она подтверждает, что все обязательные
контуры завершены и Joint готов к финальному закрытию.

Перед `closure_status = closed` система проверяет:

- есть инженерная привязка Joint;
- зафиксирован факт сварки;
- факт подтверждён FOREMAN;
- ОГС проверил WPS/допуск/технологическую корректность;
- выполнен контроль качества;
- дефекты, если были, закрыты;
- ремонт и повторный контроль после ремонта завершены;
- термообработка и контроль твёрдости (если требуются) приняты;
- исполнительная документация ПТО готова/принята;
- обязательные файлы и заключения приложены.

---

### 003-AM. RACI модель доменных сущностей

Для Production/Joints MVP вводится RACI-модель ответственности по ключевым
сущностям жизненного цикла Joint. Матрица по сущностям зафиксирована в решениях
**003-AB — 003-AL**; здесь — сводные архитектурные правила.

**Совместная ответственность ПТО + ОГС**

- **ПТО** и **ОГС** совместно подотчётны (**A**) за подтверждение инженерной
  привязки Joint (`engineering_status = confirmed`).
- **ПТО** подотчётен за Project, EngineeringDocument, Line и документационный контур.
- **ОГС** отвечает за технологическую корректность: WPS, допуск сварщика, материал,
  способ, параметры стыка.
- **DocumentationPackage** — связанный объект учёта передачи комплектов; не входит
  в базовый список из 10 RACI-сущностей (см. 003-F, 003-AL).

**Ответственность СМР за факт**

- **СМР** — ответственный (**R**) за фиксацию `WeldOperation`, ремонтных операций
  и термообработки на объекте.
- **FOREMAN** подтверждает факт сварки; без подтверждения FOREMAN производственный
  факт не считается завершённым для закрытия.
- Факт сварки не блокируется из-за непроверенного допуска, но до закрытия требует
  review ОГС (см. 003-P, 003-O).

**Ответственность ОТК / НК за контроль**

- **ОТК** подотчётен (**A**) за `Inspection`, `Defect`, приёмку и `RepairOperation`
  как производственное решение о годности.
- **НК** отвечает за выполнение и протоколы методов НК в рамках `Inspection`;
  **NDTInspection** и **HardnessInspection** — специализированные расширения
  `Inspection`, а не отдельные пункты базового RACI-списка (см. 003-S, 003-W).

**Файлы и закрытие**

- **Attachment / DocumentFile** — единый файловый механизм; ответственность определяется
  владельцем связанной бизнес-сущности (см. 003-X, 003-AK).
- **Joint closure** — процесс финального закрытия стыка; **CLOSURE_RESPONSIBLE**
  подотчётен (**A**) за `closure_status = closed`, не подменяя ПТО, ОТК, НК, ОГС
  или СМР и не заменяя файловый контур (см. 003-Z, 003-AL).
- До закрытия должны быть завершены: инженерная привязка, факт сварки, review ОГС,
  контроль, ремонт (если был), термообработка и твёрдость (если требуются), ИД ПТО,
  обязательные вложения.

Полная RACI-таблица по 10 MVP-сущностям — см.
[[docs/project/ARCHITECTURE_SESSIONS#Architecture Session 003 — RACI модель Production/Joints MVP|Session 003 — RACI]].

**Итог ADR-008:** ADR-008 завершает Architecture Session 003 и является основанием
для проектирования Production/Joints MVP.

---

### Последствия

- Целевая схема `engineering.*` должна включать `engineering_documents`,
  `lines`, `engineering_document_lines`, `documentation_packages`, `joints`,
  справочники типов соединения и материалов.
- Целевая lifecycle-модель вокруг Joint должна включать: `weld_operations`,
  `inspections`, `ndt_inspections`, `hardness_inspections`, `defects`,
  `repair_operations`, `heat_treatment_operations`, `heat_treatment_operation_joints`,
  `document_files`, `attachments`.
- Для закрытия стыка вводится отдельный контур `closure_status` и роль
  `CLOSURE_RESPONSIBLE` как финальный подтверждающий контур.
- RACI-модель Production/Joints MVP (003-AB — 003-AM) задаёт ответственность
  по доменным сущностям для проектирования RBAC и workflow.
- ADR-007 сохраняет силу по `joint_id`, жизненному циклу и неизменяемости истории;
  правила появления Joint и иерархия уточняются через `EngineeringDocument` и
  статусы `draft` / `confirmed`.
- Реализация в коде — после завершения Session 003 и синхронизации документации.

## ADR-009. Production/Joints MVP — физическая модель БД, события и API

### Контекст

Session 003 (ADR-008) зафиксировала каноническую предметную модель Production/Joints
MVP. Session 004 переводит её в физическую схему PostgreSQL, границы модулей backend,
контракт REST API и правила переходов состояний.

Источники требований: реальные журналы сварки, ремонта, контроля, термообработки,
справочники типов соединений, данные сварщиков и материалов.

Код, миграции и тесты **не менялись** в рамках Session 004.

### Решение

#### Схемы и владение данными

| Схема | Сущности |
|-------|----------|
| `project` | Project, Line |
| `engineering` | EngineeringDocument, DocumentRevision, Joint |
| `production` | WeldOperation, RepairOperation, HeatTreatmentOperation |
| `quality` | Inspection, Defect |
| `documents` | DocumentFile, технические связи файлов |
| `hr`, `welding` | существующие контуры (без изменений) |

- **Joint** — инженерная сущность в `engineering`; центральный объект процесса.
- Производственные факты — `production`; контроль и дефекты — `quality`;
  файлы — `documents`.
- `engineering_status` хранится на Joint; `production_state` и `ready_for_welding`
  **вычисляются** API, в БД не хранятся.

#### Joint

- Двухэтапное создание: **FOREMAN** / **MASTER** создаёт `DRAFT`; **ПТО** подтверждает.
- Бизнес-ключ: `project_id` + `engineering_document_id` + `joint_no` (уточняет ADR-008, 003-I).
- `engineering_status`: `DRAFT`, `CONFIRMED`, `CANCELLED`, `SUPERSEDED`.
- При новой ревизии РД: неизменившийся Joint сохраняет UUID; удалённый — `CANCELLED`;
  заменённый — `SUPERSEDED` + `superseded_by_joint_id`; существенно изменённый — новый UUID.
- Геометрия (`geometry_type`) и форма шва (`weld_type`) разделены; материалы — каталог
  + исторический снимок на каждую сторону.

#### WeldOperation

- Несколько операций на Joint; этапы MVP: `ROOT`, `FILL`, `COVER`, `FILL_COVER`.
- `actual_welder_id` и `documented_welder_id` разделены (ADR-002).
- Допуск сварщика проверяется **строго** перед созданием операции; обход в MVP не предусмотрен.
- `Joint.planned_wps_id` (ОГС) и `WeldOperation.actual_wps_id` (факт) разделены.
- Статусы: `DRAFT`, `CONFIRMED`, `VOIDED`; подтверждённая операция неизменяема;
  исправление — новая операция с `replaces_operation_id`.
- Сварочные материалы — снимок в `weld_consumable_usages` (техническая таблица).

#### Контроль, ремонт, термообработка

- **Inspection** едина для всех методов (`VT`, `RT`, `UT`, `PT`, `MT`, `HARDNESS`, `PMI`, `FERRITE`).
- Подтверждённый `FAIL` требует минимум один **Defect**.
- **RepairOperation** связывается с Defect; ремонтная сварка — `WeldOperation` с
  `repair_operation_id`; Defect закрывается повторным `PASS`, не самим ремонтом.
- **HeatTreatmentOperation** — повторяемое событие; контроль твёрдости — `Inspection.HARDNESS`.
- Роль `HEAT_TREATMENT_OPERATOR` для регистрации термообработки.

#### API

Группы: `/api/v1/projects`, `/engineering`, `/production`, `/quality`, `/documents`.

Сущности — самостоятельные коллекции; команды `confirm` / `void` / `cancel` / `supersede`;
`PATCH` только для черновиков. Ответ Joint включает вычисляемые поля состояния.

#### Импорт Excel

Не входит в начальный MVP; отложен до стабилизации модели. Окончательный вариант
(прямой импорт или через промежуточную проверку) — отдельное будущее решение.

### Отклонённые варианты

1. **Хранение `production_state` как редактируемого поля** — отклонено: риск расхождения с фактами.
2. **Отдельные сущности NDTInspection / HardnessInspection в MVP** — отклонено: единая Inspection.
3. **Создание WeldOperation без проверки допуска** — отклонено: строгая проверка обязательна.
4. **Импорт Excel в начальном MVP** — отложено.
5. **Физическое удаление подтверждённых производственных записей** — отклонено.

### Последствия

- Потребуется добавить схемы `project`, `engineering`, `production`, `quality`, `documents`.
- Потребуется новая роль `HEAT_TREATMENT_OPERATOR`.
- Реализацию нужно разделить на несколько последовательных этапов (implementation plan).
- `hr` и `welding` остаются каноническими владельцами работников, сварщиков, допусков и WPS.
- Будущий импорт Excel **не должен** обходить доменные проверки.
- ADR-008 сохраняет силу по предметной модели; ADR-009 уточняет физическую реализацию.

## ADR-010. Joint MVP — расширенная модель, двойное согласование, история ревизий и bulk-импорт

Дата: 2026-07-11

Статус: **принято** (замещает Joint-часть ADR-009; решения ADR-009
по EngineeringDocument и DocumentRevision **сохраняют силу**)

Замещает частично: [[docs/project/DECISIONS#ADR-009. Production/Joints MVP — физическая модель БД, события и API|ADR-009]] (только раздел Joint)

Уточняет: [[docs/project/DECISIONS#ADR-008. Каноническая модель предметной области WeldPassport (Session 003)|ADR-008]] ·
[[docs/project/ADR-007-joint-lifecycle-and-engineering-model|ADR-007]] · IP-05, IP-07, IP-08

Канон реализации: [[docs/project/IMPLEMENTATION_PLAN_ENGINEERING_JOINTS_MVP|Engineering Joints MVP — Implementation Plan]] (Tasks 5A, 5B, 6, 7)

### Контекст

ADR-009 (Session 004) зафиксировал минимальную модель Joint: одностадийное
подтверждение ПТО, статусы `DRAFT / CONFIRMED / CANCELLED / SUPERSEDED`, бизнес-ключ
`project_id + engineering_document_id + joint_no`, тонкая техническая связь
`joint_revision_links`. При проработке реализации выявлена потребность в более
полной модели производственного стыка:

- раздельное согласование двух служб — **ПТО** (документарная зона) и **ОГС**
  (технологическая зона), с автоматическим переходом в рабочее состояние только
  при подтверждении обеими;
- устойчивая идентичность Joint при выпуске новых ревизий инженерного документа с
  **неизменяемыми снимками** параметров на момент связи;
- **массовый ввод** стыков из одной ревизии документа с гарантией атомарности и
  идемпотентности.

Эти требования расходятся с Joint-частью ADR-009 и по правилу AGENTS.md фиксируются
отдельным ADR **до** написания кода. ADR-010 замещает **только** раздел Joint
ADR-009; решения ADR-009 по `EngineeringDocument` и `DocumentRevision` (реализованы
в Task 4, commit `6d2ea09`) остаются в силе без изменений.

### Решение

#### Базовые соглашения (Р-1 — Р-4)

- **Р-1. `hr.worker_roles.scope_type`** — значение `ENGINEERING_DOCUMENT` добавляется
  **аддитивно** к фактическому набору `GLOBAL, COMPANY, PROJECT, SITE, LINE`.
  Значения `COMPANY` и `SITE` сохраняются. Переименования и миграции данных нет
  (значения `ISOMETRIC`/`UNIT` в текущей схеме не существует). При
  `scope_type = ENGINEERING_DOCUMENT` поле `scope_id` содержит id `EngineeringDocument`
  (строковый UUID); отдельное поле не вводится.
- **Р-2. Роли** — используются существующие технические `role_code` `PTO_ENGINEER`
  (предметно «ПТО») и `OGS_ENGINEER` (предметно «ОГС»). Новые `role_code` `PTO`/`OGS`
  **не** вводятся (IP-07). Создавать Joint могут `MASTER`, `FOREMAN`, `PTO_ENGINEER`,
  `OGS_ENGINEER`; подтверждать ПТО — только `PTO_ENGINEER`; подтверждать ОГС —
  только `OGS_ENGINEER`.
- **Р-3. Сущности** — используются фактические `Line` (`project.lines`, не
  «ProjectLine»), `Project` (`project.projects`, PK UUID, есть `code`), `Worker`
  (`hr.workers`, PK Integer). Поля-акторы Joint (`created_by`, `pto_decided_by`,
  `submitted_by`, …) — Integer без FK, в стиле существующих `created_by`.
- **Р-4. Справочники отсутствуют** — ссылки на материалы (`material_id_*`),
  номенклатуру (`component_item_id_*`) и WPS (`planned_wps_id` / method) хранятся как
  **nullable UUID без FK**; текстовые дубли (`material_text_*`, `component_text_*`) —
  строки. FK добавляются отдельным решением после появления доменов МТО/WPS.

#### Согласованность иерархии Joint (Б-3)

- `Joint.line_id` — **обязателен** (NOT NULL).
- Если `EngineeringDocument.line_id` **заполнен**, он **обязан совпадать** с
  `Joint.line_id`.
- Если `EngineeringDocument.line_id IS NULL`, документ **разрешено** использовать как
  основание Joint; линия берётся из `Joint.line_id`. Такой документ обязан
  принадлежать тому же `Project`, что и Joint.
- Полная цепочка проверок при создании Joint и каждой новой связи: Project
  существует; Line существует и относится к Project; DocumentRevision существует и
  относится к EngineeringDocument; EngineeringDocument относится к тому же Project;
  соответствие Line — по правилу выше.
- Тип документа-основания **не** ограничивается `ISOMETRIC`.

#### Вычисляемые поля (Б-4)

Вычисляемые поля ADR-009 **сохраняются** (не колонки БД, вычисляются API):

- `ready_for_welding` — готовность стыка к сварке по заполненности инженерных полей;
- `missing_welding_requirements` — перечень недостающих полей;
- `production_state` — в MVP константа `NOT_STARTED`.

`requires_review` их **не** заменяет — это отдельный вычисляемый признак
согласования: `requires_review = true`, если ПТО **или** ОГС не подтвердили Joint
(`pto_status != CONFIRMED` или `ogs_status != CONFIRMED`, а также в состояниях
`DRAFT` / `PENDING_REVIEW`).

#### Модель Joint (заменяет раздел Joint ADR-009)

- Схема `engineering`; `id` UUID PK; обязательные `project_id`, `line_id`,
  `origin_document_revision_id`, `current_document_revision_id`.
- `system_code` формируется системой (`<project_code>-JNT-<sequence>`),
  не принимается от пользователя; последовательность отдельная на проект, номера не
  переиспользуются; `UNIQUE(project_id, system_code)`.
- `joint_no` (исходное обозначение) + `joint_no_normalized` (служебное: trim,
  схлопывание пробелов, типографские дефисы → `-`, сравнение без учёта регистра);
  исходное значение не теряется.
- `origin_document_revision_id` неизменяем; `current_document_revision_id` меняется
  только командой `set-current-revision` (не обычным PATCH).
- Статусы `status`: `DRAFT, PENDING_REVIEW, ACTIVE, CANCELLED, SUPERSEDED` (без
  `ON_HOLD`). Двойное согласование `pto_status` / `ogs_status`:
  `PENDING / CONFIRMED / REJECTED`. При создании `status=DRAFT`, оба статуса
  `PENDING`. `ACTIVE` — автоматически при обоих `CONFIRMED`; иначе не ACTIVE.
- `superseded_by_joint_id` — nullable self-FK; обязателен при `status=SUPERSEDED`;
  запрет self-supersede; заменяющий Joint того же проекта.
- Инженерные поля по сторонам соединения, классификация
  (`geometry_type` `BUTT/FILLET/TEE/LAP/SLOT/OTHER`, `weld_joint_type`
  `BW/SW/FW/OTHER`, `connection_code` `C/U/T/N/P/OTHER`), проектные способы сварки
  (`required_root/fill/cap_method`), требование термообработки, положение на чертеже
  (координаты необязательны; при заполненных `position_x/y` обязателен
  `coordinate_system`).
- Concurrency — `version` (optimistic locking); изменяющий запрос передаёт ожидаемую
  версию, несовпадение → конфликт без перезаписи. Физического удаления нет,
  DELETE-endpoint не создаётся.
  > **Уточнено ADR-011 (Р-11-2):** в Task 5B единая `version` разделяется на три —
  > `record_version` (concurrency, = прежняя `version`), `approval_version`,
  > `workflow_version`. См. [[docs/project/ADR-011-joint-lifecycle-approvals-blocking-scope|ADR-011 §15]].

#### Разделение ответственности ПТО / ОГС

- Поля ПТО: `joint_no`, `line_id`, документ/ревизия, `sheet_no`, `drawing_zone`,
  координаты, `location_note`, документарное примечание.
- Поля ОГС: `geometry_type`, `weld_joint_type`, `connection_code`, DN/толщины,
  материалы, компоненты, проектные способы сварки, WPS (при наличии ссылки),
  требования термообработки.
- Изменение полей ПТО сбрасывает `pto_status` → `PENDING`; полей ОГС → `ogs_status`
  → `PENDING`; общих полей — оба; из `ACTIVE` Joint возвращается в `PENDING_REVIEW`.

#### История ревизий: `joint_document_revisions`

- Неизменяемый снимок основных параметров Joint на момент связи; `revision_role`
  (`ORIGIN/CONFIRMED/MODIFIED/REMOVED`), `document_role`
  (`PRIMARY/ADDITIONAL/EXECUTIVE/REFERENCE`), `link_status` (`ACTIVE/INVALIDATED`).
- Снимок не редактируется (PATCH snapshot не создаётся); исправление — новая связь
  или аннулирование (`invalidated_reason/by/at`); аннулированная связь остаётся в
  истории и не может стать текущей PRIMARY.
- В пределах одной `DocumentRevision` `joint_no_normalized` уникален среди
  **активных** связей (partial unique index `WHERE link_status='ACTIVE'`); у одного
  Joint в момент времени только одна активная связь `document_role=PRIMARY`,
  соответствующая `current_document_revision_id`.

#### Доступ по областям (scope) и иерархия

- Области: `GLOBAL, PROJECT, COMPANY, SITE, LINE, ENGINEERING_DOCUMENT`. Проверяется
  не только совпадение `scope_id`, но и иерархия; для обычных действий — по текущему
  документу Joint; для смены текущей ревизии — доступ и к старому, и к новому
  документу. Несколько активных ролей дают объединение областей.

#### Bulk-импорт и идемпотентность

- `POST /api/v1/engineering/joints/bulk` — атомарное создание из одной
  `DocumentRevision`; ≤ 500 строк; при любой невалидной строке не создаётся ни один
  Joint; ошибки с `row_index`; `system_code` присваивается только после успешной
  валидации всего пакета; commit/rollback целиком.
- Таблица `engineering.joint_bulk_requests` (`UNIQUE(project_id, idempotency_key)`,
  `request_hash`, `response_payload` JSON): тот же ключ и тот же hash → сохранённый
  ответ; тот же ключ, другой hash → конфликт; ответ хранится целиком и не
  пересобирается из текущего состояния Joint.

#### Разбиение реализации на этапы

| Этап | Содержание | Миграция |
|------|-----------|----------|
| **Task 5A — Joint Core** | `joints`; обязательная связь с Line; `origin_/current_document_revision_id`; `system_code`; основные инженерные поля; нормализация `joint_no`; `version`; вычисляемые `ready_for_welding`, `missing_welding_requirements`, `production_state`; create / get / list / PATCH только допустимых полей | `20260711_05_engineering_joints` |
| **Task 5B — Joint Review Lifecycle** | `PENDING_REVIEW` / `ACTIVE`; `pto_status` / `ogs_status`; submit / confirm / reject; cancel / supersede; роли `PTO_ENGINEER` / `OGS_ENGINEER`; аддитивное добавление `ENGINEERING_DOCUMENT` в `scope_type` | `20260711_06_joint_review` |
| **Task 6 — Joint ↔ DocumentRevision History** | `joint_document_revisions`; неизменяемые снимки; роли связей; invalidate; set-current-revision | `20260711_07_joint_doc_revisions` |
| **Task 7 — Bulk Joint Import** | bulk endpoint; `joint_bulk_requests`; идемпотентность; атомарность пакета | `20260711_08_joint_bulk_requests` |

### Отклонённые варианты

1. **Реализовать всё как единый Task 5** — отклонено: объём охватывает несколько
   доменных подсистем; поэтапная сдача с ревью безопаснее.
2. **Одностадийное подтверждение (только ПТО) из ADR-009** — отклонено для Joint:
   производству требуется раздельная ответственность ПТО и ОГС.
3. **Буквальное `scope_type` из первичного ТЗ (рейнейм `ISOMETRIC`, набор с `UNIT`)**
   — отклонено: таких значений в схеме нет; исполнение удалило бы `COMPANY`/`SITE`.
4. **Новые `role_code` `PTO`/`OGS`** — отклонено (IP-07); используются существующие
   `PTO_ENGINEER` / `OGS_ENGINEER`.
5. **Редактируемый снимок связи (PATCH snapshot)** — отклонено: снимок неизменяем,
   исправление — новая связь или аннулирование.

### Последствия

- Joint-часть ADR-009 считается замещённой ADR-010; остальные разделы ADR-009 и вся
  реализация Task 4 (`EngineeringDocument`, `DocumentRevision`) — без изменений.
- Появляются таблицы `engineering.joints`, `engineering.joint_document_revisions`,
  `engineering.joint_bulk_requests`; `hr.worker_roles.scope_type` расширяется
  значением `ENGINEERING_DOCUMENT`.
- `IMPLEMENTATION_PLAN` перестраивается на этапы 5A / 5B / 6 / 7.
- Материалы, номенклатура и WPS остаются без FK до появления соответствующих
  доменов.
- ADR-010 является каноном реализации Joint для Tasks 5A, 5B, 6 и 7.

## ADR-011. Жизненный цикл Joint, согласования, блокировки и контроль областей

Дата: 2026-07-11

Статус: **принято** (детализирует Task 5B поверх [[docs/project/DECISIONS#ADR-010. Joint MVP — расширенная модель, двойное согласование, история ревизий и bulk-импорт|ADR-010]]; базовую идентичность Joint не меняет)

Область: Engineering / Joint / ПТО / ОГС

Полный текст: [[docs/project/ADR-011-joint-lifecycle-approvals-blocking-scope|ADR-011-joint-lifecycle-approvals-blocking-scope.md]].

Уточняет: [[docs/project/DECISIONS#ADR-010. Joint MVP — расширенная модель, двойное согласование, история ревизий и bulk-импорт|ADR-010]] ·

### Суть

- **Жизненный цикл Joint:** `DRAFT → PENDING_REVIEW → ACTIVE`, терминальные `CANCELLED`
  и `SUPERSEDED` (необратимы). Переходы — только доменными командами, не правкой поля.
- **Независимые согласования ПТО и ОГС** (`NOT_SUBMITTED / PENDING / APPROVED /
  REJECTED / REVOKED`); `ACTIVE` — автоматически и атомарно при действующих `APPROVED`
  обеих сторон для текущей `approval_version`. Согласования не объединяются в одно поле.
- **Выборочный сброс:** изменение инженерных данных сбрасывает ПТО, технологических —
  ОГС, общих — оба; незатронутая сторона сохраняет решение.
- **Автосогласование ОГС** (`AUTOMATIC` / `REJECTED` / `MANUAL_REVIEW_REQUIRED`);
  преодоление формального запрета — только `CHIEF_WELDER` через `OVERRIDE` с обоснованием.
- **Три версии Joint:** `record_version` (concurrency), `approval_version` (значимые
  данные), `workflow_version` (workflow); конфликт → `409 Conflict` без автоповтора.
- **Блокировки** — отдельные записи с областью (`PRODUCTION / EDITING / APPROVAL /
  ALL`); не статус ЖЦ. Готовность действий (`available_actions`) **вычисляется**
  сервером, не хранится и не дублируется во frontend.
- **Отмена и замена:** штатная `CANCELLED` (после первой `WeldOperation` — совместное
  решение ПТО_MANAGER + CHIEF_WELDER); атомарная `SUPERSEDED` через
  `REPLACEMENT_PENDING`; производственные события на преемника **не переносятся**;
  ошибочная отмена — новый Joint через `recreated_from_joint_id`.
- **Переоценка одного Joint** по зонам `ENGINEERING` / `WELDING_TECHNOLOGY` (`NDT`,
  `PWHT`, `EXECUTIVE_DOCUMENTATION` — архитектурно предусмотрены, логика позже).
- **Аудит и авторство:** поля-акторы не принимаются из тела запроса — только из
  auth-контекста; история статусов, согласований, блокировок и переоценок неизменяема.

Обязательный объём Task 5B (§44) и отложенные расширения (§45, приложение E)
разграничены. Расхождения словарей с ADR-010 **закрыты** архитектурными решениями
Р-11-1 — Р-11-4 (раздел «Решения по согласованию с ADR-010» полного текста):
состояния согласования — набор ADR-011, положительное решение `APPROVED`; версии —
три (`record`/`approval`/`workflow`, `version → record_version`); роли — техимена
ADR-010 (`PTO_ENGINEER`/`OGS_ENGINEER`) + новые `PTO_MANAGER`/`CHIEF_WELDER`/`AUDITOR`;
`scope_type` — набор ADR-010 (`ISOMETRIC → ENGINEERING_DOCUMENT`, `UNIT → SITE`).
Общая линия: словари и физическая схема — по ADR-010, полнота жизненного цикла — по
ADR-011.

## ADR-012. WeldOperation как неизменяемый производственный факт сварки

Дата: 2026-07-12

Статус: **принято** — закрывает Architecture Session 005 (решения 005-A — 005-CE)

Architecture Session: [[docs/project/ARCHITECTURE_SESSIONS#Architecture Session 005|Session 005]]

Замещает частично: [[docs/project/DECISIONS#ADR-009. Production/Joints MVP — физическая модель БД, события и API|ADR-009]] (только раздел WeldOperation и связанные правила допуска при создании операции)

Уточняет: [[docs/project/DECISIONS#ADR-008. Каноническая модель предметной области WeldPassport (Session 003)|ADR-008]] (003-P, 003-O) ·
[[docs/project/ADR-002-double-welder-accounting|ADR-002]] ·
[[docs/project/ADR-006-domain-ownership-matrix|ADR-006]] ·
[[docs/project/ADR-007-joint-lifecycle-and-engineering-model|ADR-007]] ·
[[docs/project/DECISIONS#ADR-010. Joint MVP — расширенная модель, двойное согласование, история ревизий и bulk-импорт|ADR-010]] ·
[[docs/project/DECISIONS#ADR-011. Жизненный цикл Joint, согласования, блокировки и контроль областей|ADR-011]]

Канон: [[docs/project/ARCHITECTURE_SESSIONS#Architecture Session 005|Architecture Session 005]]

### Контекст

После завершения инженерного контура `Project → Line → EngineeringDocument →
DocumentRevision → Joint` (Task 7) требуется определить модель фактического
выполнения сварки.

Нельзя смешивать:

- инженерную сущность `Joint`;
- работу конкретного сварщика;
- технологическое принятие ОГС;
- последующую корректировку данных.

Ранее ADR-009 (Session 004) зафиксировал упрощённую физическую модель
`WeldOperation` (единый статус, этапы `ROOT`/`FILL`/`COVER`, строгая блокировка
создания при отсутствии допуска, исправление через `replaces_operation_id`).
Session 005 и настоящий ADR уточняют канон производственного факта без отмены
центральной роли Joint и разделения плановой / фактической WPS из ADR-009.

### Решение

Принять следующие правила:

- одна `WeldOperation` = один `Joint` + один фактический сварщик + один
  классифицированный этап (`root`, `fill`, `cap`, `back_weld`, `tack`) + один
  фактически применённый способ сварки;
- производственный факт **сохраняется** даже при нарушении допуска, WPS, клейма
  или иных технологических требований; нарушение классифицируется и направляется
  ОГС, технологическое принятие блокируется;
- `lifecycle_status`, `welder_confirmation_status` и `ogs_review_status` —
  **раздельные** оси состояния; единый статус не используется;
- завершённая операция (`lifecycle_status = completed`) **неизменяема**; прямое
  редактирование запрещено;
- исправления завершённого факта выполняются только через отдельную сущность
  `WeldOperationCorrection` с атомарным применением и переводом исходной операции
  в `superseded`;
- полная переварка оформляется как новая `WeldOperation` с признаком `reweld`;
  **локальный ремонт** проектируется отдельно и **не входит** в Task 8;
- WPS хранится на `Joint` (актуальный план) и на `WeldOperation` (фактически
  применённая версия); после первой завершённой операции смена WPS — только через
  технологическую ревизию;
- проверка допуска и WPS выполняется при создании, значимом изменении, завершении
  и после корректировки; при несоответствии факт не стирается, а создаёт маршрут
  review ОГС;
- подтверждение участия сварщика фиксирует мастер / прораб; сварщику не обязателен
  доступ в систему; история подтверждений неизменяема;
- интеграция с МТО, ОТК и НК реализуется через явные границы: временная ручная
  фиксация материалов до МТО; `InspectionApplicabilityDecision` для применимости
  результатов контроля при замене операции;
- реализация разбита на последовательные задачи **8A — 8F**; к Task 8A переходят
  только после принятия Session 005 и ADR-012.

### Отклонённые варианты

1. **Блокировка создания WeldOperation при отсутствии допуска** (ADR-009, 004-12) —
   отклонено: противоречит принципу сохранения производственного факта (ADR-008,
   003-P; Session 005).
2. **Единый статус операции** — отклонено: смешивает lifecycle, подтверждение
   сварщика и review ОГС.
3. **Прямое редактирование завершённой операции** — отклонено: нарушает
   трассируемость и двойной учёт сварщика.
4. **Исправление только новой WeldOperation с `replaces_operation_id`** без
   `WeldOperationCorrection` (ADR-009, 004-13) — отклонено: недостаточно для
   согласований, снимков и атомарного применения.
5. **Включение локального ремонта в Task 8** — отклонено: отдельный контур
   `RepairOperation` / `Defect`.

### Последствия

**Положительные:**

- полная трассируемость производственного факта и решений ОГС;
- невозможно незаметно переписать исполнителя или клеймо завершённой операции;
- сохраняются нарушения, несоответствия и маршруты review;
- поддерживается идемпотентный импорт и разрешение конфликтов;
- поддерживаются корректировки, supersede и полная переварка (`reweld`);
- сохраняется связь с будущими модулями контроля, НК и МТО через явные границы.

**Ограничения:**

- реализация требует нескольких последовательных задач (8A — 8F);
- полный lifecycle `RepairOperation`, `Defect`, Inspection и NDT **не входят** в
  Task 8;
- модель корректировок сложнее обычного CRUD;
- завершённые операции нельзя редактировать напрямую;
- физическая схема `production.weld_operations` из ADR-009 потребует пересмотра
  при реализации Task 8A.

## ADR-013. Импорт XLSX и разрешение конфликтов (Task 8E)

Дата: 2026-07-13

Статус: **принято**

Architecture Session: [[docs/project/ARCHITECTURE_SESSIONS#Architecture Session 005|Session 005]] (импорт: типы источников, идемпотентный ключ, конфликт → корректировка)

Уточняет: [[docs/project/DECISIONS#ADR-012. WeldOperation как неизменяемый производственный факт сварки|ADR-012]] ·
[[docs/project/DECISIONS#ADR-010. Joint MVP — расширенная модель, двойное согласование, история ревизий и bulk-импорт|ADR-010]]

### Контекст

Task 8A–8D сформировали канонический контур `WeldOperation`, включая lifecycle,
подтверждение сварщика, результат ОГС и корректировки (Task 8D). Для загрузки данных
из внешнего XLSX потребовался отдельный импортный контур, который:

- не изменяет существующие `Joint` и `WeldOperation`;
- не использует correction/supersede-механизмы Task 8D;
- предварительно проверяет и сопоставляет данные;
- разрешает конфликты до записи в производственные таблицы;
- обеспечивает полный аудит и происхождение данных.

### Решение

Принять отдельный импортный контур:

```text
XLSX → ImportSession → ImportRow → ImportGroup → matching/resolution → apply → Joint/WeldOperation
```

Основные решения:

1. Источник MVP — только канонический XLSX-шаблон WeldPassport с обязательным
   `template_version`.
2. Одна строка источника может содержать данные `Joint` и одной `WeldOperation`.
3. Прямая запись из XLSX в производственные таблицы запрещена — только через staging.
4. Подготовка импорта выполняется через staging-контур.
5. Техническая роль `OGS_ENGINEER` реализует архитектурную роль `WELDING_ENGINEER`
   (новых role_code в `hr.worker_roles` не вводится).
6. Только `CHIEF_WELDER` может выполнить окончательный apply.
7. Сопоставление `Joint` выполняется сначала по `project_id` и нормализованному
   номеру стыка, затем уточняется по линии, изометрии и ревизии.
8. Расхождения инженерных данных создают конфликт и не изменяют существующий `Joint`.
9. Изменение существующей `WeldOperation` через импорт запрещено; для этого
   используется механизм Task 8D.
10. Полный дубликат операции пропускается идемпотентно (`SKIPPED_DUPLICATE`).
11. Атомарная единица применения — `ImportGroup`: один `Joint` и все связанные
    импортируемые операции.
12. Ошибка одной бизнес-независимой группы не откатывает ранее успешно применённые
    независимые группы.
13. Частичное применение разрешено.
14. `ImportResolution` хранит неизменяемую историю ручных решений (supersede-цепочка,
    не путать с supersede-механизмом Task 8D).
15. `ImportProvenance` хранится отдельно и не добавляет import-поля в `Joint` или
    `WeldOperation`.
16. Исходный файл — неизменяемый артефакт с SHA-256 (сверка при каждом чтении).
17. Хранение файлов абстрагировано через `FileStorage`; локальный адаптер — для
    разработки/тестов, S3-совместимый адаптер включается конфигурацией.
18. Команды импорта поддерживают идемпотентность (ключ — заголовок `Idempotency-Key`).
19. Применение в MVP выполняется синхронно (без фоновых очередей).
20. Физическое удаление import-сессий, provenance и истории запрещено.

### Физическая модель

Миграция `20260712_13_import_pipeline` (следует единственному Alembic head, второго
head не вводит) создаёт 11 таблиц схемы `engineering` (по ORM-моделям
`import_models.py`):

```text
engineering.import_sessions
engineering.import_parse_attempts
engineering.import_groups
engineering.import_rows
engineering.import_row_changes
engineering.import_resolutions
engineering.import_apply_attempts
engineering.import_apply_group_results
engineering.import_provenance
engineering.import_status_events
engineering.import_idempotency_keys
```

FK на `joints`/`weld_operations` — `RESTRICT`; дочерние таблицы импорта — `CASCADE`
на `import_sessions` (каскад только техническая целостность; доменное удаление
сессии запрещено).

### Реализация

Новые модули `app/engineering/`:

- `import_workflow.py` — словари статусов/кодов, роли, чистые функции пересчёта;
- `import_models.py` — 11 ORM-таблиц;
- `import_storage.py` — `FileStorage` + локальный и S3 адаптеры;
- `import_parse.py` — разбор XLSX и нормализация;
- `import_matching.py` — сопоставление Joint и классификация дублей;
- `import_repository.py` — доступ к данным;
- `import_schemas.py` — Pydantic-схемы;
- `import_services.py` — оркестрация;
- `import_api.py` — HTTP-слой.

Итоги:

- 24 API endpoint;
- 31 интеграционный тест (`tests/test_import_pipeline.py`);
- регрессия: `639 passed`;
- один Alembic head: `20260712_13_import_pipeline`.

### Последствия

Положительные:

- импорт отделён от производственного lifecycle;
- существующие производственные данные не изменяются молча;
- обеспечены аудит, идемпотентность и provenance;
- допускается безопасное частичное применение;
- Task 8D остаётся единственным механизмом корректировки операций.

Ограничения MVP:

- только канонический XLSX;
- нет произвольного сопоставления legacy-колонок;
- apply синхронный;
- UI не входит;
- локальный storage допустим только как адаптер разработки;
- расширенная аналитика и фоновые очереди отложены.

## ADR-014. Heat Treatment Integration (Task 8F)

Дата: 2026-07-13

Статус: **принято**

Architecture Session: [[docs/project/ARCHITECTURE_SESSIONS#Architecture Session 006|Session 006]] (термическая обработка: цикл, участие Joint, снимок карты, актуальность)

Уточняет: [[docs/project/DECISIONS#ADR-012. WeldOperation как неизменяемый производственный факт сварки|ADR-012]] ·
[[docs/project/DECISIONS#ADR-011. Жизненный цикл Joint, согласования, блокировки и контроль областей|ADR-011]]

> Номер: изначально задание называло ADR-013, но ADR-013 занят импортом (Task 8E),
> поэтому Task 8F зафиксирован как **ADR-014**.
>
> Переопределение Task 8F: ранний план описывал «Task 8F — Integration Boundaries»
> (границы МТО/ОТК/НК, `InspectionApplicabilityDecision`). Фактически Task 8F
> реализован как **Heat Treatment Integration**; прежнее наполнение «Integration
> Boundaries» вынесено в отдельный будущий этап.

### Контекст

WeldPassport должен учитывать **фактическую термическую обработку** сварных
соединений, не смешивая её:

- с импортом XLSX (Task 8E);
- с корректировками `WeldOperation` (Task 8D);
- с контролем качества и НК;
- с полным контуром метрологии и управления оборудованием.

Один фактический цикл термообработки может охватывать **несколько** сварных
соединений. Технологические требования к режиму должны браться из утверждённой
технологической карты термообработки, а не повторно вводиться по каждому стыку.

### Решение

1. `HeatTreatmentProcedureRevision` — минимальная утверждаемая редакция
   технологической карты термообработки (нейтральное имя, не `WPS`: `WPS`
   означает технологию сварки).
2. `HeatTreatmentBatch` — общий фактический цикл термообработки.
3. `HeatTreatmentOperation` — участие одного `Joint` в конкретном цикле.
4. Один `HeatTreatmentBatch` может включать несколько `Joint`.
5. Одна строка журнала соответствует одной `HeatTreatmentOperation`.
6. Общий результат цикла и индивидуальный результат по каждому `Joint`
   учитываются раздельно.
7. Цикл обязательно связывается с утверждённой редакцией технологической карты
   до запуска.
8. При запуске сохраняется неизменяемый снимок ключевых требований карты
   (`procedure_snapshot`).
9. После начала цикла его состав и ссылка на карту блокируются.
10. Повторная термообработка всегда оформляется новым циклом и новой операцией со
    ссылкой на предыдущую (`previous_heat_treatment_operation_id`,
    причина `REPEAT_AFTER_REJECTION`).
11. Отклонённая или историческая запись не переписывается.
12. Актуальность принятой термообработки определяется **вычисляемо** относительно
    актуальной завершённой `WeldOperation` (последняя `COMPLETED`, не заменённая).
13. Новая сварка или ремонт не удаляет прежний результат, но делает его
    неактуальным для текущего состояния соединения.
14. Журнал термической обработки — **отчётное представление**, а не отдельная
    первичная бизнес-таблица.
15. Контроль качества после термообработки остаётся отдельным контуром (Task 8F
    добавляет только интеграционное правило готовности `Joint`).

### Жизненный цикл общего цикла (`HeatTreatmentBatch.status`)

- `DRAFT` — Черновик;
- `PLANNED` — Запланировано;
- `IN_PROGRESS` — Выполняется;
- `COMPLETED` — Физически выполнено, но ещё не принято;
- `REVIEWED` — Проверено ОГС;
- `CLOSED` — Полностью закрыто;
- `CANCELLED` — Отменено;
- `REJECTED` — Отклонено ОГС.

Основной путь: `DRAFT → PLANNED → IN_PROGRESS → COMPLETED → REVIEWED → CLOSED`.
Дополнительно: `DRAFT/PLANNED → CANCELLED`, `COMPLETED → REJECTED`.

### Результаты ОГС (`review_result`, отдельно от workflow-статуса)

- `PENDING` — Ожидает решения;
- `ACCEPTED` — Принято;
- `ACCEPTED_WITH_JUSTIFICATION` — Принято с инженерным обоснованием;
- `REJECTED` — Отклонено.

Индивидуальный результат по `Joint` (`HeatTreatmentOperation.result`) использует
те же значения плюс `NOT_APPLICABLE`. Достаточность подтверждающих данных
(`evidence_sufficiency`) ограничивает допустимый результат: `INSUFFICIENT`
запрещает любое принятие, `PARTIALLY_SUFFICIENT` допускает только
`ACCEPTED_WITH_JUSTIFICATION`/`REJECTED`/`NOT_APPLICABLE`.

### Роли (существующий канон, новых не вводится)

- инженерный результат термообработки принимает `OGS_ENGINEER` (техническая роль
  ОГС/инженера-сварщика) или `CHIEF_WELDER`;
- оператор/мастер/прораб — `MASTER`, `FOREMAN`, `CHIEF_WELDER` — создают цикл,
  формируют состав, планируют, запускают, вносят фактические параметры,
  завершают, загружают документы, регистрируют отклонения;
- ОТК (`OTK_INSPECTOR`) может просматривать цикл/документы и регистрировать
  отклонения, но не принимает инженерный результат.

### Граница MVP

В Task 8F **не входят**:

- `JointProductionState`;
- полноценный конструктор технологических карт;
- управление установкой термообработки;

## ADR-015. Inspection and NDT Workflow Canon (Session 007)

Дата: 2026-07-13

Статус: **принято** — закрывает Architecture Session 007 (решения 007-01 — 007-27).
Канон утверждён; **Tasks 9A — 9C реализованы**. Task 9C завершает ядро выполнения
назначенных методов контроля и регистрации лабораторных заключений. Tasks
**9D — 9G** — planned / not implemented. Отложена только **детальная реализация
импорта** результатов НК — до Architecture Session 008.

Architecture Session: [[docs/project/ARCHITECTURE_SESSIONS#Architecture Session 007|Session 007]]

Замещает частично: [[docs/project/DECISIONS#ADR-009. Production/Joints MVP — физическая модель БД, события и API|ADR-009]] (только раздел Inspection: единая сущность с результатами `PASS`/`FAIL`/`CONDITIONAL`)

Уточняет: [[docs/project/DECISIONS#ADR-012. WeldOperation как неизменяемый производственный факт сварки|ADR-012]] ·
[[docs/project/DECISIONS#ADR-014. Heat Treatment Integration (Task 8F)|ADR-014]] ·
[[docs/project/ADR-006-domain-ownership-matrix|ADR-006]]

Канон: [[docs/project/ARCHITECTURE_SESSIONS#Architecture Session 007|Architecture Session 007]]

> Номер: ADR-013 занят импортом (Task 8E), ADR-014 — термообработкой (Task 8F),
> поэтому канон контроля/НК зафиксирован как **ADR-015**.

### Контекст

Контур контроля качества и НК был **осознанно отложен** в Session 005 (решения
005-U, 005-W, 005-BR) и упрощённо описан в ADR-009 как единая сущность `Inspection`
с результатами `PASS`/`FAIL`/`CONDITIONAL`. Реального промышленного контроля этого
недостаточно: нужно разделить заявку на контроль, назначение и выполнение методов,
технический результат лаборатории и технологическое решение ОГС, отчёты,
первичные материалы, групповые выборки, зоны частичного контроля и влияние контроля
на состояние `Joint`.

Основной инициатор и создатель заявки на контроль — **ОГС**. СМР фиксирует готовность
соединения; ОГС формирует заявку; ОТК проверяет результаты; лаборатория НК выполняет
назначенные методы.

### Решение

Принять канон контроля качества и НК (полный текст — Session 007, решения
007-01 — 007-27):

- основной контур: `Joint → Inspection → назначение методов → выполнение контроля →
  технические результаты → проверка ОТК → решение ОГС → состояние Joint → журнал`;
- **Inspection** — заявка/контрольное мероприятие для одного `Joint` либо
  утверждённой групповой выборки; lifecycle
  `DRAFT → REQUESTED → ASSIGNED → IN_PROGRESS → COMPLETED → REVIEWED → CLOSED`
  (+ `SUSPENDED`, `CANCELLED`, `TERMINATED`);
- методы контроля моделируются цепочкой **InspectionMethodAssignment** (назначение) →
  **InspectionMethodExecution** (фактическое выполнение; несколько на назначение) →
  **InspectionMethodResult** (технический результат:
  `CONFORMING`/`NONCONFORMING`/`INCONCLUSIVE`/`NOT_EVALUATED`,
  lifecycle `DRAFT → SUBMITTED → VERIFIED` + `SUPERSEDED`/`CANCELLED`);
  реализовано как `MethodExecutionResultItem` внутри `MethodExecution`, терминал
  выполнения — `LAB_CONFIRMED` (см. «Реализация Task 9C» ниже);
- **технический результат лаборатории (`InspectionMethodResult`) и технологическое
  решение ОГС (`InspectionDecision`) хранятся раздельно**; лаборатория фиксирует
  результат, ОТК переводит его в `VERIFIED`, ОГС принимает решение уровня
  `RESULT`/`INSPECTION` (`ACCEPT`/`REJECT`/`REPEAT_INSPECTION`/`SEND_TO_REPAIR`);
- **InspectionSample** — групповая выборка `Joint`, после начала контроля неизменяема;
- **InspectionCoverage** — структурированная зона частичного контроля;
- **InspectionReport** — официальный протокол/заключение
  (`DRAFT → ISSUED → VERIFIED` + `PRELIMINARY`/`SUPERSEDED`/`CANCELLED`);
  предварительный отчёт не закрывает контроль; один отчёт может включать несколько
  `Joint`/методов/результатов;
- **InspectionEvidence** — первичные материалы (снимки, УЗК-файлы, фото ВИК, схемы);
- **Defect** — лаборатория фиксирует индикацию, ОТК подтверждает и классифицирует,
  ОГС принимает технологическое решение; полный ремонтный lifecycle — отдельно;
- **NdtLaboratoryProfile** — участие лаборатории через `project_companies` с ролью
  `ndt_lab`; `Company` остаётся юрлицом; профиль хранит разрешённые методы и статус;
- методы `VT`/`RT`/`UT`/`PT`/`MT` (ВИК — в общем контуре `Inspection`); системные
  коды неизменяемы; проект ограничивает набор, но не меняет смысл;
- **требуемый** контроль (на `Joint`) и **назначенный** контроль (в
  `InspectionMethodAssignment`) разделены; отклонение — только с обоснованием ОГС;
  требования уже созданной заявки задним числом не пересчитываются;
- готовность `Joint` к контролю рассчитывается системой, фиксируется СМР,
  подтверждается ОГС; условия делятся на **блокирующие** и **предупреждающие**;
- повторный контроль без ремонта — внутри того же `Inspection`; после
  ремонта/переварки — новый `Inspection`; обязательный контроль после термообработки
  требует явной связи `Inspection ↔ HeatTreatmentOperation`;
- влияние на `Joint` — **вычисляемое** `inspection_state`
  (`NOT_REQUIRED`/`PENDING`/`IN_PROGRESS`/`PASSED`/`FAILED`/`REPAIR_REQUIRED`/`REINSPECTION_REQUIRED`);
  основной lifecycle `Joint` не переписывается каждым результатом; `PASSED` — только
  после окончательных принятых результатов по всем обязательным методам;
- нумерация `<PROJECT_CODE>-INS-<SEQUENCE>` + внешние номера ОГС и лаборатории;
- нормативные основания: проектные `EngineeringDocument`/`DocumentRevision` и внешние
  `NormativeDocument`/`NormativeDocumentRevision`; в заявке — снимок обозначения,
  редакции и пункта;
- файлы: метаданные и контрольные суммы в PostgreSQL, файлы — в объектном хранилище;
  доступ через короткоживущие подписанные ссылки; замена файла = новая версия; доступ
  по роли/scope/проекту/типу; rate limit (по пользователю и по файлу) → `429` +
  `Retry-After`;
- журнал контроля — представление из канонических сущностей (XLSX/PDF/CSV/JSON), а не
  ручной регистр; для закрытых периодов — неизменяемые снимки
  (`DRAFT → GENERATED → VALIDATED → APPROVED → PUBLISHED` + `SUPERSEDED`/`CANCELLED`);
- реализация разбита на Tasks **9A — 9G**; к Task 9A переходят только после принятия
  Session 007 и ADR-015.

### Роли (существующий канон, новых role_code не вводится)

- ОГС / `WELDING_ENGINEER` (техническая роль `OGS_ENGINEER`) — создаёт `Inspection`,
  выбирает методы, назначает лабораторию, подтверждает основания, принимает
  технологические решения;
- ОТК (`OTK_INSPECTOR`) — проверяет технические результаты, подтверждает дефекты,
  проверяет документы, подтверждает контрольную часть;
- лаборатория НК — выполняет методы, фиксирует результаты, выпускает отчёты,
  прикладывает первичные материалы (участие через `project_companies` role `ndt_lab`);
- `CHIEF_WELDER` — глобальные административные права, критические исключения;
- СМР — фиксирует готовность `Joint`;
- ПТО — предоставляет проектные требования, получает отчёты и журналы.

**Соответствие ролей.** Бизнес-наименование роли инженера-сварщика/ОГС —
`WELDING_ENGINEER`; существующий технический `role_code` backend — `OGS_ENGINEER`.
Новый `role_code` **не вводится**.

### Эволюция результатов контроля (историческая совместимость)

- значения результата контроля `PASS`/`FAIL`/`CONDITIONAL` из ADR-009 (004-14)
  остаются **историческим проектным вариантом**;
- ADR-015 **заменяет** их для будущей реализации;
- исторически предложенные в Session 007 технические результаты `InspectionMethodResult`:
  - `CONFORMING`;
  - `NONCONFORMING`;
  - `INCONCLUSIVE`;
  - `NOT_PERFORMED` — историческое имя, заменённое в реализации Task 9C на
    `NOT_EVALUATED`;
- реализованный `MethodExecutionResultItem` использует `NOT_EVALUATED`: оценка ещё
  не сформирована. `CONTROL_NOT_PERFORMED` означает, что контроль не выполнен; это
  отдельный тип отмены, а не оценка результата.

### Эволюция Defect (историческая совместимость)

- прежняя схема `quality.defects` из ADR-009 является **предварительным черновиком**;
- для будущей реализации действует канон ADR-015:
  `индикация лаборатории → подтверждение и классификация ОТК → Defect → решение ОГС`;
- полный ремонтный lifecycle остаётся **вне** Session 007 и **вне** Task 9E.

### Граница импорта (интеграционное требование верхнего уровня)

Импорт результатов контроля (XLSX, CSV, PDF, API лаборатории) зафиксирован **только
как интеграционное требование верхнего уровня**: импорт **не может автоматически
принимать результат**. Детальная архитектура импорта (форматы, разбор протоколов,
PDF-извлечение, интеграция с API лабораторий, staging/сопоставление/конфликты/провенанс,
правила ручного подтверждения) относится к будущей **Architecture Session 008** и в
ADR-015 не проектируется.

### Отклонённые варианты

1. **Единая `Inspection` с результатом `PASS`/`FAIL`/`CONDITIONAL`** (ADR-009,
   004-14) — отклонено на уровне метода: не разделяет назначение, выполнение,
   технический результат и решение ОГС. Значение сохранено как исторический контекст;
   технический результат метода теперь `InspectionMethodResult`.
2. **Совмещение технического результата лаборатории и решения ОГС в одной записи** —
   отклонено: нарушает разделение ответственности лаборатории/ОТК/ОГС и трассируемость.
3. **Хранимый ручной статус контроля `Joint`** — отклонено: состояние контроля
   `inspection_state` **вычисляется** (принцип 004-23), основной lifecycle `Joint` не
   переписывается каждым результатом.
4. **Проектирование детального импорта XLSX/CSV/PDF в Session 007** — отклонено:
   вынесено в Architecture Session 008; в Session 007 — только интеграционное
   требование верхнего уровня.
5. **Отдельный ручной регистр «Журнал контроля»** — отклонено: журнал — отчётное
   представление из канонических сущностей.

- полная трассируемость контроля: назначение → выполнение → результат → решение ОГС;

- [[docs/project/DECISIONS#ADR-012. WeldOperation как неизменяемый производственный факт сварки|ADR-012]] — готовность и актуальность относительно актуальной завершённой `WeldOperation`; `reweld` → новый `Inspection`;
- [[docs/project/DECISIONS#ADR-014. Heat Treatment Integration (Task 8F)|ADR-014]] — обязательный контроль после термообработки, связь `Inspection ↔ HeatTreatmentOperation`;
- [[docs/project/DECISIONS#ADR-009. Production/Joints MVP — физическая модель БД, события и API|ADR-009]] — прежняя единая `Inspection` (раздел частично замещён);
- [[docs/project/ADR-006-domain-ownership-matrix|ADR-006]] — владельцы доменов (ОТК — контроль, НК — методы, ОГС — решение).

### Актуализация ADR-019

ADR-019 замещает внутреннюю проверку ОТК, обязательное подтверждение Defect ОТК,
совместное решение ОГС/ОТК и безусловное согласование Repair внутренним ОТК.
Не замещаются: Result ≠ Finding ≠ Defect, версионность, история, отдельный Repair,
Reinspection, документы качества и подтверждаемая причинная связь со сварщиком.

## ADR-016. Quality Execution Model (Task 9C)

Дата: 2026-07-15

Статус: принято, реализовано

### Контекст

ADR-015 зафиксировал проектный канон контроля, но реализация Task 9C уточнила
границы агрегатов, правила редакций, модель лабораторного заключения и внешних
участников. Эти уточнения должны быть каноном текущей физической архитектуры, не
переписывая историческую запись Architecture Session 007.

### Решение

- `MethodExecution` отделён от `InspectionMethodAssignment`: назначение отвечает на
  вопрос «что и кому назначено», выполнение — «что фактически выполнено в конкретном
  эпизоде контроля».
- Результаты контроля (`MethodExecutionResultItem`) версионируются. История не
  переписывается; исправления создаются через revision с lineage-полями
  `root_result_item_id`, `revision_no`, `supersedes_result_item_id`.
- Сам `MethodExecution` также исправляется новой редакцией, а подтверждённая редакция
  остаётся неизменяемой.
- `LaboratoryConclusion` — отдельный агрегат, а не поле выполнения. Заключение
  ссылается на конкретную редакцию одного или нескольких подтверждённых
  `MethodExecution`; исправление выпущенного заключения создаёт новую редакцию.
- Внешние лаборатории моделируются существующими `project.companies` и участием в
  проекте через `project_companies` с ролью `NDT_LAB`; отдельный профиль юрлица не
  вводится.
- Внешние контролёры и утверждающие лица моделируются как `QualityExternalPerson` и
  не являются `hr.Worker`.
- `LaboratoryAccreditation` связывается с лабораторией, имеет срок действия, а при
  выпуске заключения её реквизиты фиксируются неизменяемым snapshot.
- `LAB_CONFIRMED` означает подтверждение лабораторного результата или регистрацию
  внешнего лабораторного документа и не является решением ОТК. `VERIFIED`
  зарезервирован для будущего этапа проверки ОТК и в Task 9C не реализован.
- `NOT_EVALUATED` означает, что оценка результата ещё не сформирована;
  `CONTROL_NOT_PERFORMED` означает, что контроль не выполнен. Эти состояния не
  взаимозаменяемы.

### Последствия

- Task 9C завершает ядро выполнения назначенных методов контроля и регистрации
  лабораторных заключений. Цепочка исполнения трассируется как назначение →
  выполнение → локальные результаты → лабораторное заключение, с отдельной историей
  редакций каждого изменяемого факта.
- `quality_audit_events` фиксирует доменные действия Quality; API Task 9C работает с
  актуальными агрегатами `MethodExecution` и `LaboratoryConclusion`.
- Tasks **9D — 9G** (решения ОГС/ОТК, дефекты, evidence/файлы, журналы) остаются
  planned / not implemented.
- Исторические имена `InspectionMethodExecution`, `InspectionMethodResult` и
  `InspectionReport` сохраняются только в записях прежнего канона и ссылках на их
  замену.

> Номер: ADR-015 занят каноном контроля/НК, ADR-016 — моделью выполнения (Task 9C),
> поэтому канон решений по качеству, дефектов, ремонта и документов качества
> зафиксирован как **ADR-017**.

### Контекст

ADR-015 (Session 007) зафиксировал контур контроля и НК до получения технического
результата, ADR-016 (Task 9C) — модель фактического выполнения методов и
лабораторных заключений. Оставался неопределённым **процесс после получения
результата контроля**: как отрицательный результат превращается (или не
превращается) в подтверждённый дефект, кто и как принимает решение по качеству, как
устроен ремонт и повторный контроль, как ведутся документы качества.

Основной контур Session 008:

```text
Inspection Result — результат контроля
        ↓
Quality Finding — обнаруженный признак
        ↓
Engineering Evaluation — инженерная оценка
        ↓
Defect — подтверждённый дефект
        ↓
Quality Decision — решение по качеству
        ↓
Repair — ремонт
        ↓
Reinspection — повторный контроль
        ↓
Defect Closure — закрытие дефекта
```

### Проблема

- отрицательный результат контроля ошибочно приравнивался к дефекту;
- не были разделены технический результат, обнаруженный признак и подтверждённый
  дефект;
- отсутствовал канон совместного решения ОГС и ОТК, разрешения разногласий главным
  сварщиком, версионирования и обоснования решений;
- не были определены жизненные циклы `Defect`, `Repair`, `Reinspection` и единая
  модель документа качества.

### Решение

Принять канон Session 008 (полный текст — Session 008, блоки 008-01 — 008-05):

**008-01. Result ≠ Finding ≠ Defect.** Три разные сущности:

- `Inspection Result` — технический факт метода; **не** содержит решения о ремонте,
  окончательной оценки, признания дефекта или разрешения дальнейшего производства;
- `Quality Finding` — обнаруженный исполнителем НК/лабораторией признак; создание
  Finding **не** означает автоматического признания дефекта;
- `Defect` — несоответствие, признанное недопустимым **только после инженерной
  оценки**. Отрицательный результат контроля может существовать без `Defect`
  (например `RT: FAILED → Engineering Review → индикация допустима → ACCEPT →
  Defect отсутствует`).

**008-02. Quality Decision.** Инженерная оценка Finding выполняется совместно: ОГС —
техническая и технологическая оценка, ОТК — соответствие нормативам и требованиям
качества; решения фиксируются раздельно. Итоговые решения:
`ACCEPT` / `REPAIR_REQUIRED` / `REINSPECTION_REQUIRED` / `REJECT`. При разногласии
ОГС и ОТК — `Chief Welder Review → Final Decision` с обязательным обоснованием.
Решения после фиксации **не редактируются** — только новая версия с обязательной
причиной; старая версия остаётся в истории. Для каждого решения (включая `ACCEPT`)
обязательны нормативный документ, пункт/критерий приёмки, текстовое обоснование,
автор, дата и время. Решение принимается **отдельно по каждому** Quality Finding;
итог Inspection рассчитывается автоматически по самому строгому активному решению
(`REJECT > REPAIR_REQUIRED > REINSPECTION_REQUIRED > ACCEPT`). Главный сварщик может
выполнить override рассчитанного итога с обоснованием; автоматически рассчитанный
итог сохраняется отдельно от изменённого. Отменить итоговое решение может только
главный сварщик, затем выбирает: вернуть Finding на повторную оценку ОГС и ОТК либо
сразу установить новое итоговое решение.

**008-03. Defect.** Создаётся только после явного подтверждения ОГС и ОТК; ведётся
совместно, владелец инженерной сущности — ОГС, ОТК — обязательный участник
подтверждения, проверки и контроля закрытия. Связь `Quality Finding ↔ Defect` —
**многие-ко-многим**. Defect содержит тип (из отдельного расширяемого справочника,
не зашитого только в код), описание, локализацию, размеры, нормативные
классификаторы, критичность (`MINOR` / `MAJOR` / `CRITICAL`). Изменение критичности
и локализации — только новой версией инженерной оценки с причиной. Локализация
обязательно связана с `Joint` и конкретной зоной шва и содержит структурированные
поля и текстовое уточнение. Причина может быть неизвестна при создании, но должна
быть установлена до закрытия (категория, коренная причина, пояснение; ОГС определяет
техническую причину, ОТК подтверждает достаточность анализа). Корректирующее
действие обязательно для критических и повторяющихся дефектов; для критического
повторяющегося Defect закрытие блокируется до выполнения действия (исключение — по
обоснованному решению главного сварщика). Жизненный цикл — см. ниже.

**Повторяемость** определяется настраиваемым версионируемым правилом (тип дефекта,
сварщик, WPS, материал, диаметр, толщина, участок, проект, период). ОГС формирует
правило, главный сварщик утверждает; система выявляет возможную повторяемость, ОГС
подтверждает или отклоняет; уведомляются ОГС, ОТК и главный сварщик.

**Связь Defect с WeldOperation и сварщиком.** Связь с `Joint` обязательна; **прямая
связь Defect со сварщиком не создаётся** — только через
`Defect → WeldOperation → Welder`. Причинная связь с `WeldOperation` — отдельное
инженерное решение с уровнем уверенности `POSSIBLE` / `PROBABLE` / `CONFIRMED` (ОГС
устанавливает/меняет, ОТК подтверждает достаточность доказательств, история — по
версиям). `POSSIBLE`/`PROBABLE` — аналитические сигналы; для персональной
ответственности используется только `CONFIRMED`.

**008-04. Repair.** Отдельная сущность; связь `Defect ↔ Repair` —
**многие-ко-многим**. Выполненный Repair **не** означает автоматического устранения
Defect. Мастер создаёт заявку, ОГС оформляет и утверждает план, ОТК согласовывает;
главный сварщик подключается при критическом дефекте, превышении лимита, разногласии
или исключении. План структурирован (связанные Defect, зона, технология, WPS, способ
выборки, требования к сварщикам, материалы, методы и объём повторного контроля,
нормативное основание); для сварочного Repair WPS обязателен (исключение — по
обоснованию главного сварщика), для несварочного не требуется. Назначенный и
фактический исполнитель фиксируются отдельно; для сварочного Repair неподходящий
допуск блокирует назначение. После утверждения план неизменяем — изменения только
новой версией с повторным утверждением ОГС и согласованием ОТК. Отклонения от плана
фиксируются отдельно (`MINOR DEVIATION` / `MAJOR DEVIATION`). Повторный контроль
разрешается только после `COMPLETED`. Лимиты ремонтов считаются отдельно:
`Defect Repair Count`, `Joint Repair Count`, `Repair Zone Count`; при превышении
новый Repair блокируется (исключение — по обоснованию главного сварщика).

**Reinspection.** Каждый Reinspection связывается с конкретным Repair (один
Reinspection может покрывать несколько Repair в одной зоне и объёме; один Repair
может требовать несколько методов). Итог рассчитывается автоматически по самому
строгому результату; главный сварщик может изменить с обоснованием (исходный расчёт
сохраняется). После принятого Reinspection и отдельных подтверждений ОГС и ОТК
система автоматически переводит Defect в `CLOSED_AFTER_REPAIR`. При неудачном
Reinspection главный сварщик выбирает новую попытку Repair или окончательное
отклонение Joint; предыдущие Repair и Reinspection сохраняются.

**Quality State Joint.** При окончательном отклонении Joint не удаляется и не
переводится в обычный `CANCELLED`, а получает качество-состояние
`REJECTED — отклонено по качеству`: история сохраняется, производственные действия
блокируются, новые Repair и Inspection не запускаются без отдельного решения.
Снять это состояние может только главный сварщик новой версией решения при наличии
новых подтверждённых данных, технического и нормативного обоснования и причины;
после снятия блокировки автоматически не снимаются — маршрут (повторная оценка /
новый ремонт / повторный контроль / возврат в производство) выбирается отдельно.

**008-05. Quality Document.** Единая сущность документа качества, связываемая
одновременно с `Inspection`, `Quality Finding`, `Defect`, `Repair`, `Reinspection`
и другими объектами; один файл не дублируется для каждой связи. Категории:
`WORKING` / `EVIDENCE` / `OFFICIAL` (тип и статус хранятся раздельно).
Версионирование: файл выпущенной версии не перезаписывается, предыдущая получает
`SUPERSEDED`. Владение обязательно (подразделение-владелец, ответственное лицо,
автор, источник); схема утверждения настраивается по типу; `ISSUED` возможен только
после прохождения схемы; выпущенный документ неизменяем. Подписи: `WORKING` — без
обязательной ЭП; `EVIDENCE` — автор, время загрузки, источник; `OFFICIAL` — ЭП или
формализованное электронное утверждение. Для каждого файла хранится контрольная
сумма (при совпадении новая физическая копия не создаётся — создаётся новая связь).
Удаление: `WORKING` — до утверждения; `EVIDENCE`/`OFFICIAL` физически не удаляются
(связь можно отменить / перевести в `CANCELLED`). Обязательный комплект документов
настраивается (проект, тип процесса, критичность, норматив); ОГС определяет
технические документы, ОТК — документы качества, главный сварщик утверждает правило;
Defect и Repair сохраняют ссылку на применённую версию правила. Система формирует
единый **реестр документов качества**; экспорт — Excel (рабочий) и PDF (официальный
реестр с ЭП/контрольной суммой/QR-кодом); публично доступны только базовые сведения,
полные данные и сам PDF — по правам.

### Архитектурные границы

- Session 008 определяет **процесс после получения результата контроля** и не
  переопределяет модель выполнения контроля (ADR-016) и контур заявки/НК (ADR-015).
- `Inspection Result` (ADR-015/016) остаётся техническим фактом; Session 008
  добавляет над ним слой `Finding → Evaluation → Decision → Defect → Repair →
  Reinspection → Closure`.
- В канон **не входят** (см. «Исключения»): печатные формы и макеты PDF, генераторы
  документов, реализация ЭП, публичный API проверки подлинности, frontend, backend,
  миграции, импорт документов, реализация уведомлений и фактическая реализация
  Defect/Repair/Reinspection.
- **Импорт результатов НК** (XLSX/CSV/PDF/API лаборатории), ранее прогнозно
  привязанный к «Architecture Session 008», в эту сессию **не вошёл** и остаётся
  открытым для отдельной будущей архитектурной сессии (см. раздел «Связь с Session
  007»).

### Роли и ответственность

- **ОГС / `WELDING_ENGINEER`** — техническая и технологическая оценка, владелец
  инженерной сущности Defect, оформление и утверждение плана Repair, техническая
  причина, техническое заключение по ремонту.
- **ОТК / `OTK_INSPECTOR`** — соответствие нормативам и требованиям качества,
  обязательный участник подтверждения Defect, согласование плана Repair, подтверждение
  качества и результата.
- **Главный сварщик / `CHIEF_WELDER`** — разрешение разногласий, override и отмена
  итоговых решений, критические исключения, утверждение правил повторяемости и
  комплектности, отмена подтверждённого Defect и качество-состояния `REJECTED` —
  всегда с обязательным обоснованием и сохранением истории.
- **Мастер** — заявка на ремонт, перевод в `IN_PROGRESS`, фиксация физического
  завершения, инициирование остановки/возобновления/отмены.
- **Лаборатория НК** — повторный контроль (Reinspection) по назначенным методам.
- Новые `role_code` **не вводятся**.

### Жизненные циклы

**Defect:** `DRAFT → CONFIRMED → REPAIR_REQUIRED → REINSPECTION_REQUIRED →
CLOSURE_PENDING → CLOSED_AFTER_REPAIR / CLOSED_AS_ACCEPTABLE`; плюс
`REJECTED` (не подтвердился/ошибочно создан) и `CANCELLED` (запись/процесс отменены
по другой причине) — эти два различаются. `CONFIRMED` — только после подтверждений
ОГС и ОТК; отменить подтверждённый Defect может только главный сварщик.

**Repair:** `DRAFT → PLANNED → APPROVED → IN_PROGRESS → PAUSED → REWORK_REQUIRED →
PERFORMED → VERIFICATION_PENDING → COMPLETED`; плюс `REJECTED` (попытка отклонена) и
`CANCELLED`. `RESUMED — возобновлён` фиксируется как **событие**, а не обязательно
как отдельное длительное состояние. `COMPLETED` — после подтверждений ОГС и ОТК и
закрытия всех активных замечаний.

**Quality Document:** `DRAFT → UNDER_REVIEW → APPROVED → ISSUED → SUPERSEDED /
CANCELLED`.

Английские статусы сопровождаются русскими пояснениями в
[[docs/project/UBIQUITOUS_LANGUAGE|Ubiquitous Language]] (Раздел 10).

### Последствия

**Положительные:**

- строгое разделение технического результата, признака и подтверждённого дефекта;
- прослеживаемая ответственность ОГС/ОТК/главного сварщика с обоснованием и
  версиями;
- явные жизненные циклы Defect/Repair/Reinspection и единая модель документа
  качества без дублирования файлов;
- аналитика повторяемости и причинности без несправедливой персональной
  ответственности (только `CONFIRMED`).

**Ограничения:**

- Session 008 фиксирует только канон; реализация — Tasks **9D — 9K** (planned / not
  implemented);
- блок **008-06 «Печатные формы»** остаётся открытым;

  будущей сессии;
- физическая схема (таблицы, миграции, API) в ADR-017 не фиксируется.

### Исключения из текущего объёма

## ADR-019. External Quality Acceptance and Welding Responsibility Canon

Дата: 2026-07-16

Статус: **ACCEPTED — принято**

Частично замещает: [[docs/project/DECISIONS#ADR-015. Inspection and NDT Workflow Canon (Session 007)|ADR-015]] ·
[[docs/project/DECISIONS#ADR-017. Quality Decision, Defect, Repair and Quality Documents Canon (Session 008)|ADR-017]]

Не изменяет: [[docs/project/DECISIONS#ADR-016. Quality Execution Model (Task 9C)|ADR-016]] ·
[[docs/project/DECISIONS#ADR-018. Electronic Documents and Printed Forms Canon (Session 008-06)|ADR-018]]

Согласованный источник дизайна:
[[docs/superpowers/specs/2026-07-16-adr-019-external-quality-acceptance-responsibility-design|Модель ответственности за качество и внешней приёмки]].

### Контекст

Отдельного ОТК подрядчика нет; технические решения принимает главный сварщик,
официальную приёмку выполняет внешний орган, а ОГС регистрирует решение в MVP.
Поэтому внутренняя техническая оценка, внешняя приёмка и ответственность сварщика
должны быть разделены.

### Решение

- Laboratory Result / Conclusion не равно внешней приёмке.
- Engineering Evaluation и Chief Welder Decision принадлежат ОГС.
- External Acceptance Decision имеет бинарный итог `ГОДЕН` / `НЕ ГОДЕН`.
- Автор внешнего решения, регистратор ОГС и проверяющий разделены.
- Предварительная запись без документа не влияет на Joint.
- Техническая блокировка и внешняя приёмка независимы.
- Новая сварка, ремонт или переварка прекращает актуальность прежней приёмки.
- Требование внешней приёмки задаётся версионируемым правилом проекта.
- `OTK_INSPECTOR` выводится из активной внутренней цепочки совместимо.
- Defect и ответственность сварщика требуют отдельной технической оценки.

### Роли и границы ответственности

| Участник | Ответственность | Не выполняет |
|---|---|---|
| Лаборатория НК | Измерения, индикации и необязательное собственное заключение о соответствии | Не принимает Joint от имени заказчика |
| ОГС | Техническая оценка результатов и несоответствий | Не подменяет внешнюю приёмку |
| Главный сварщик или официальный делегат | Дополнительный контроль, признание Defect, Repair, переварка, технология, `TechnicalHold` и внутреннее закрытие | Не становится автором решения заказчика |
| Уполномоченный сотрудник ОГС | Подготовка оценки; регистрация внешнего решения и документа | Не решает от имени внешнего инспектора |
| Внешний орган приёмки | Решение по методу контроля и/или итоговая приёмка Joint | Не отменяет `TechnicalHold` ОГС |
| Сварщик | Участник фактической сварочной операции | Не признаётся ответственным автоматически из-за Defect или внешнего отказа |

### Концептуальная модель

| Сущность | Назначение |
|---|---|
| `LaboratoryConclusion` | Результаты лаборатории; вывод о соответствии допустим, но не обязателен |
| `EngineeringEvaluation` | Техническая оценка ОГС |
| `ChiefWelderDecision` | Дополнительный контроль, Repair, переварка, внутреннее закрытие или запрет |
| `ExternalAcceptanceAuthority` | Уполномоченная организация проекта: ОТК заказчика, стройконтроль, технический надзор и т. п. |
| `ExternalInspectorSnapshot` | Неизменяемый снимок ФИО, организации, должности/роли и реквизитов документа-основания внешнего автора; контакты и реквизиты доверенности необязательны |
| `ExternalAcceptanceDocument` | Документ-основание для решений по одному или нескольким Joint |
| `ExternalAcceptanceDecision` | Версионное решение по методу или Joint: `ГОДЕН` / `НЕ ГОДЕН` |
| `TechnicalHold` | Временная либо постоянная внутренняя техническая блокировка |
| `ResponsibilityAssessment` | Оценка причин и персональной причинной связи |
| `DecisionDelegation` | Делегирование полномочий главного сварщика по проекту, сроку и командам |

Физические имена таблиц, классов, enum и API-команд определяются планом реализации.

### Лабораторный результат и внешнее решение

Лаборатория может передать только измерения и индикации либо дополнительно своё
заключение. Отрицательное заключение создаёт `TechnicalHold` и задачу ОГС, но не
внешний итог `НЕ ГОДЕН`. Виды и объём контроля задаются версионируемыми правилами;
лаборатория выполняет программу, но не меняет её.

Внешнее решение относится к конкретному методу/результату либо к итоговой приёмке
Joint. Положительные решения по методам не создают итог `ГОДЕН` автоматически.
Результат строго бинарный; состояние оформления хранится отдельно: предварительное,
ожидает документа, ожидает проверки, подтверждено, заменено или отозвано.

Предварительная запись без документа не действует. Для активации нужны документ и
внутренняя проверка. Если регистратор — главный сварщик, отдельная проверка не
нужна; иначе регистратор и проверяющий — разные лица. Запись раздельно хранит
внешнего автора и его полномочия, регистратора ОГС, проверяющего и даты действий.
Внешний инспектор может не иметь `worker` или `user_account`; сохраняется его
неизменяемый снимок с ФИО, организацией, должностью/ролью и реквизитами
документа-основания. Контакты и реквизиты доверенности необязательны.

### Правила закрытия Joint

| Условие проекта | Условия закрытия качества |
|---|---|
| Внешняя приёмка обязательна | Актуальный итог `ГОДЕН` и отсутствие `TechnicalHold` |
| Получено `НЕ ГОДЕН` | Закрытие блокируется независимо от внутренней оценки |
| Получено `ГОДЕН`, но действует `TechnicalHold` | Закрытие блокируется |
| Внешняя приёмка не требуется | Главный сварщик или делегат закрывает качество после контроля, устранения Defect и снятия блокировок; основание хранится явно |

### Документы и версии решений

Допустимый вид документа задаёт проект. Решение ссылается на документ, страницу или
лист и при необходимости строку/позицию Joint; один документ может подтверждать
несколько решений. Различаются электронный оригинал, электронная копия и скан
бумажного оригинала; сохраняются доступные архивные реквизиты или сведения об ЭП.

Действующее решение не редактируется и не удаляется. Исправление — новая версия со
ссылкой на предыдущую, причиной замены и новым либо явно повторно подтверждённым
документом. Решение связано с циклом контроля и состоянием Joint. Новая сварочная
операция, Repair или переварка делает его историческим; после Reinspection требуется
новое внешнее решение, если оно обязательно.

### Техническое решение, Repair и делегирование

Главный сварщик определяет дополнительный контроль, Repair или переварку и
утверждает технологию. Инженер ОГС готовит оценку; окончательное решение принимает
главный сварщик либо сотрудник с действующим `DecisionDelegation`. Делегирование
содержит проект, сотрудника, срок, разрешённые команды и автора; аудит фиксирует
основание полномочия.

Предварительное согласование Repair внешним органом требуется только по правилу
проекта или договора; если оно обязательно, начать Repair до согласования нельзя.
Внешний итог `НЕ ГОДЕН` создаёт внешнее несоответствие и направляется на оценку ОГС,
но не создаёт Defect автоматически. Причины отказа структурируются с сохранением
исходной формулировки; категория «другое» требует пояснения.

### Причинная связь и ответственность сварщика

```text
Лабораторный результат → индикация → EngineeringEvaluation → Defect
→ анализ причин → коренная причина → ResponsibilityAssessment
```

Лаборатория и внешний орган не создают подтверждённый Defect автоматически. Причин
может быть несколько: подготовка, сварщик, организация работ, WPS/режим, материал,
оборудование, термообработка, среда и другое. Коренную причину утверждает главный
сварщик или делегат. Связь со сварщиком устанавливается только через фактическую
сварочную операцию и имеет уровни `POSSIBLE` / `PROBABLE` / `CONFIRMED`
(`ВОЗМОЖНАЯ` / `ВЕРОЯТНАЯ` / `ПОДТВЕРЖДЁННАЯ`). На показатели, периодику и допуск
влияет только `CONFIRMED` с мотивированным техническим заключением; вся история
исходных фактов и оценок сохраняется.

### RBAC

`OTK_INSPECTOR` выводится из активной внутренней цепочки качества, помечается как
устаревшая/зарезервированная роль и не удаляется резко из Tasks 9A–9C.

| Команда | Исполнитель |
|---|---|
| Подтвердить программу контроля | Главный сварщик или уполномоченный ОГС |
| Выполнить контроль и внести данные | Лаборатория НК |
| Провести техническую оценку | Инженер ОГС |
| Утвердить техническое решение | Главный сварщик или официальный делегат |
| Создать предварительную запись внешнего решения | Уполномоченный сотрудник ОГС |
| Подтвердить регистрацию внешнего решения | Главный сварщик или другой уполномоченный проверяющий |
| Создать новую версию решения | Уполномоченный сотрудник ОГС с последующей проверкой |
| Закрыть Joint | Закрывающая роль после автоматической проверки условий |

Внешний инспектор — автор решения как внешнее лицо, а не пользователь с ролью
`OTK_INSPECTOR`.

### Последствия

До Task 9D обновляются архитектура, словарь, roadmap и post-9C план. Tasks 9D–9K
остаются planned / not implemented и должны быть перепланированы по этому канону.
Код и миграции этим ADR не изменяются. ADR-019 частично замещает только явно
перечисленные положения ADR-015/017; модель исполнения ADR-016 и канон печатных
форм ADR-018 сохраняются.

### Контекст

WeldPassport должен обеспечить управление официальными документами сварочного
производства как **доказательствами выполнения работ**, а не только генерацию PDF.
ADR-017 (Session 008) зафиксировал канон решений по качеству, дефектов, ремонта и
документов качества, но блок 008-06 «Печатные формы» остался открытым. Session 008-06
закрывает его, вводя канон Electronic Document Management.

### Решение

Принята модель **Electronic Document Management**:

- **Preview** и **Official Document** разделены (008-06-01).
- Операционные документы и документы закрытия разделены (008-06-02).
- Ответственность выпуска определяется типом документа (008-06-03).
- Официальный документ содержит **PDF, Snapshot, Source Links и Hash** (008-06-04).
- Выпущенные документы **неизменяемы**; изменения создают **новые версии** документа
  (008-06-05).
- Источники документа связываются через универсальную модель **Document Sources**
  (008-06-06).
- Выпуск документа выполняется **после утверждения ответственного лица** (008-06-07).
- История формирования документа хранится через **Document History Events**
  (008-06-08).
- Используется **гибридная модель шаблонов документов** (008-06-09).

### Последствия

- Формируется единый слой **Electronic Documentation**.
- Task **9D — Quality Finding and Engineering Evaluation** должен использовать ссылки
  на **Official Documents**; инженерная оценка качества обязана ссылаться на
  конкретные **редакции** (Document Revision) официального документа.
- Исполнительная документация получает **версионность и аудит**.
- Реализация (генераторы PDF, конкретные макеты форм, реализация ЭП, публичный API
  проверки подлинности, backend, миграции) — **отдельными задачами**; ADR-018
  фиксирует только канон.

Ранее в проекте рассматривался модуль расчёта норм времени для операций `MARK_PIPE`,
`CUT_PIPE`, `EDGE_PREP`, `JOINT_ASSEMBLY`, `WELD_PIPE`, `QC_WELD`. Были предусмотрены
таблицы `norms.material_groups`, `norms.base_norms`, `norms.org_norms`. Однако расчёт
времени сварки для каждого сварщика требует отдельной методики, нормативной базы,
коэффициентов и согласования — на текущем этапе это слишком сложно, спорно и может
затормозить основной проект.

### Решение

Модуль нормирования времени сварочных работ **исключён из активного MVP WeldPassport**.

- Не использовать `norms.*` как часть основной бизнес-логики MVP.
- Перенести модуль в backlog / future modules.
- Материалы проектирования (`10_Проектирование_WeldPassport/10_Нормы_времени/`) и
  обсуждения в чатах сохраняются как задел на будущее — **не удалять**.

Формулировка для документации:

> Модуль нормирования времени сварочных работ исключён из активного MVP WeldPassport.
> Причина — высокая сложность и спорность расчёта времени сварки по каждому сварщику
> на текущем этапе. Модуль сохраняется как возможное будущее расширение, но активная
> архитектура MVP фокусируется на учёте работников, ролей, допусков сварщика, факта
> сварки, контроля, исполнительной документации и закрытия стыков.

### Последствия

MVP фокусируется на жизненном цикле сварочного производства:

- `hr.workers`, `hr.worker_roles`;
- `ogs` / `welding.welder_admissions`;
- `production.joints`, `production.weld_operations`;
- `periodic_kss.*`;
- результаты контроля QC / NDT;
- исполнительная документация ПТО;
- закрытие и история стыка.

Нормирование может быть возвращено позже отдельным этапом.

### Ограничение

**Не добавлять** новые зависимости активных модулей от `norms.*`.

Поле `material_groups` в `welding.welder_admissions` относится к допуску сварщика
(группы материалов по аттестации) и **не является** частью схемы `norms.*`.
