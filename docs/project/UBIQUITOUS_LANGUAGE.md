## Статус термина

Термин считается **утверждённым** только если имеет статус **«Канон»**.

Термины со статусом **«Черновик»** нельзя использовать как основу для БД, API и
бизнес-логики без отдельного архитектурного решения (Architecture Session + ADR).

---

## Назначение

**UBIQUITOUS_LANGUAGE.md** — единый словарь предметной области WeldPassport.

Все архитектурные документы, ADR, код, API, база данных и пользовательская
документация **должны** использовать определения только из этого документа.

Если термин отсутствует в словаре — он считается **неутверждённым** и не может
использоваться как каноническое имя сущности, поля API или таблицы без Architecture
Session и обновления словаря.

Документ обеспечивает одинаковое понимание терминов всеми участниками проекта:

- экспертами предметной области;
- архитекторами;
- разработчиками;
- AI;
- тестировщиками;
- аналитиками.

---

## Правила ведения словаря

Для каждого термина обязательно указывать:

| Поле | Смысл |
|------|--------|
| **Определение** | Что означает термин |
| **Владелец** | Какой домен отвечает за термин |
| **Используется** | Какие домены используют термин (если применимо) |
| **Не является** | Чем данный термин **не** является |
| **Связанные ADR** | Перечень ADR |

Новые термины и изменение определений — только через Architecture Session
([[docs/project/ARCHITECTURE_GOVERNANCE|AGF]]) с обновлением этого файла.

**Статусы записей:**

- **Канон** — определение утверждено;
- **Черновик** — заготовка, ожидает Architecture Session.

# Раздел 2. Производство

## Joint

**Статус:** Канон

### Определение

Инженерная сущность, созданная из утверждённой рабочей документации, являющаяся
**центральным объектом производственного процесса**. Хранится в `engineering.joints`.

Жизненный цикл (`status`, ADR-010/011): `DRAFT`, `PENDING_REVIEW`, `ACTIVE`,
`CANCELLED`, `SUPERSEDED` (последние два — терминальные). Независимые согласования
`pto_status`/`ogs_status` (ADR-011 Р-11-1): `NOT_SUBMITTED`, `PENDING`, `APPROVED`,
`REJECTED`, `REVOKED` — положительное решение называется **`APPROVED`** (не
`CONFIRMED`, который занят `engineering_status` документов). `ACTIVE` — автоматически
при обоих `APPROVED` для текущей `approval_version`.

Три версии (ADR-011 Р-11-2): `record_version` (concurrency), `approval_version`
(значимые данные; к ней привязаны согласования), `workflow_version` (переходы,
блокировки, замена). `ready_for_welding`, `missing_welding_requirements` и
`production_state` **вычисляются** API и в БД не хранятся.

### Владелец

Engineering (`engineering`)

### Используется

Production, Quality, NDT, Executive Documentation (Documents / PTO).

### Не является

- сварочной операцией;
- документом;
- сварщиком;
- вычисляемым производственным состоянием (`production_state`).

### Связанные ADR

ADR-006, ADR-007, ADR-008, ADR-009, ADR-010, ADR-011

## WeldOperation

**Статус:** Канон

### Определение

Неизменяемый производственный факт работы **одного фактического сварщика** на
**одном классифицированном этапе** (**один Joint + один сварщик + один этап + один
способ**). Хранится в `production.weld_operations`.

Классифицированные этапы: `root`, `fill`, `cap`, `back_weld`, `tack`. Если разные
сварщики выполняли разные этапы или один этап несколько сварщиков — отдельные
операции на каждого.

Раздельные статусы (не сводить в один):

- `lifecycle_status`: `draft`, `completed`, `superseded`, `cancelled`;
- `welder_confirmation_status`: `pending`, `confirmed`, `not_confirmed`, `not_required`;
- `ogs_review_status`: `not_required`, `pending_review`, `returned_for_clarification`,
  `accepted`, `accepted_with_remark`, `rejected`.

Завершённая операция (`completed`) неизменяема. Производственный факт сохраняется
даже при нарушении допуска, WPS или клейма; нарушение направляется ОГС. WPS на
`Joint` (план) и на операции (факт) разделены. Полная переварка — операция с
признаком `reweld`.

### Владелец

Production (`production`)

### Используется

Quality, OGS, Executive Documentation (Documents / PTO), MTO (будущая связь материалов).

### Не является

- стыком (Joint);
- технологическим решением ОГС (это отдельный review);
- локальным ремонтом (`RepairOperation`);
- корректировкой (`WeldOperationCorrection`);
- документом;
- зарплатой или стоимостью работ.

### Связанные ADR

ADR-002, ADR-006, ADR-007, ADR-008, ADR-009 (частично замещён), ADR-012

---

## WeldOperationCorrection

**Статус:** Канон

### Определение

Отдельная трассируемая сущность исправления завершённой `WeldOperation`. Хранит
исходную операцию, `before_snapshot` / `after_snapshot`, изменённые поля, причину,
согласования и ссылку на заменяющую операцию. Типы: `data_correction`,
`welder_correction`, `technology_correction`, `cancel_false_record`,
`supersede_record`, `import_conflict_resolution`.

Применение атомарно: заменяющая операция становится действующей, исходная —
`superseded`. Параллельные корректировки одной операции запрещены.

### Владелец

Production (`production`)

### Используется

OGS, SMR (согласование СМР), Quality.

### Не является

- прямым редактированием завершённой операции;
- новой первичной сваркой;
- локальным ремонтом;
- решением ОГС (решение ОГС — отдельный контур review).

### Связанные ADR

ADR-012

## Reweld

**Статус:** Канон

### Определение

Полная переварка стыка, оформляемая как новая `WeldOperation` с признаком `reweld`.
Обязательны ссылка на исходную отклонённую операцию, классифицированная причина,
решение ОГС, комментарий, автор и дата решения. Черновик `reweld` можно создать до
решения ОГС, но завершить — только после. Локальный ремонт в этот контур не входит.

### Владелец

Production (`production`)

### Используется

OGS, Quality, NDT.

### Не является

- локальным ремонтом (`RepairOperation`);
- корректировкой данных (`WeldOperationCorrection`);
- новым Joint.

### Связанные ADR

ADR-012

## WelderConfirmation

**Статус:** Канон

### Определение

Подтверждение участия фактического сварщика в `WeldOperation`, фиксируемое мастером
или прорабом от имени сварщика. Сварщику не обязателен доступ в систему. Основания:
`personal_confirmation`, `paper_weld_log`, `shift_assignment`, `production_report`,
`other` (с обязательным комментарием). История подтверждений, уточнений и отмен
неизменяема. Отсутствие подтверждения не удаляет производственный факт.

### Владелец

Production (`production`)

### Используется

OGS, Executive Documentation (Documents / PTO).

### Не является

- допуском сварщика (Admission);
- решением ОГС;
- учётной записью сварщика в системе.

### Связанные ADR

ADR-002, ADR-012

## OGSReview

**Статус:** Канон

### Определение

Технологическая проверка и решение ОГС по `WeldOperation` или
`WeldOperationCorrection`: допуск, WPS, клеймо, параметры, несоответствия.
Решения: `accepted`, `accepted_with_remark`, `rejected`, `returned_for_clarification`.
Статус review (`ogs_review_status`) отделён от lifecycle операции и подтверждения
сварщика. При отклонении производственный факт сохраняется; Joint нельзя считать
технологически принятым.

### Владелец

OGS (`welding`)

### Используется

Production, Quality, Documents.

### Не является

- контролем ОТК / НК;
- подтверждением FOREMAN;
- оформлением исполнительной документации ПТО.

### Связанные ADR

ADR-006, ADR-008, ADR-012

## InspectionApplicabilityDecision

**Статус:** Канон

### Определение

Решение о применимости существующего результата контроля после замены или
корректировки `WeldOperation`. Решения: `applicable`, `applicable_with_remark`,
`not_applicable`, `repeat_inspection_required`. Владелец: ВИК — ОТК; RT, UT, PT, MT
и другие методы — НК. При `not_applicable` Joint возвращается в ожидание контроля,
создаётся черновик требования повторного контроля. Полный lifecycle контроля в
Task 8 не входит.

### Владелец

Quality (`quality`) — ОТК для ВИК, НК для методов НК

### Используется

Production, OGS.

### Не является

- новым протоколом контроля;
- Defect;
- автоматической перепривязкой результатов к заменяющей операции.

### Связанные ADR

ADR-006, ADR-012

## Inspection

**Статус:** Канон

> **Уточнение (Session 007, ADR-015).** Определение расширено: `Inspection` —
> **заявка/контрольное мероприятие** с собственным lifecycle, а технический результат
> метода вынесен в `InspectionMethodResult` (см. Раздел 9). Прежняя трактовка ADR-009
> (единая сущность с результатом `PASS`/`FAIL`/`CONDITIONAL`) сохраняется как
> исторический контекст и **частично замещена ADR-015** на уровне метода.

### Определение

Заявка или контрольное мероприятие для одного `Joint` либо утверждённой групповой
выборки (`InspectionSample`). Основной инициатор — **ОГС**. Lifecycle:
`DRAFT → REQUESTED → ASSIGNED → IN_PROGRESS → COMPLETED → REVIEWED → CLOSED`
(+ `SUSPENDED`, `CANCELLED`, `TERMINATED`). Объединяет назначение методов
(`InspectionMethodAssignment`), их выполнение, отчёты, решение ОГС и подтверждённые
`Defect`. Методы: `VT`/`RT`/`UT`/`PT`/`MT` (ВИК — в общем контуре).

### Владелец

Quality (`quality`) / ОГС (инициатор заявки)

### Используется

Production, Documents, Reporting.

### Не является

- `WeldOperation`;
- Executive Documentation;
- техническим результатом метода (это `InspectionMethodResult`);
- технологическим решением ОГС (это `InspectionDecision`).

### Связанные ADR

ADR-006, ADR-008, ADR-009, ADR-015

## Defect

**Статус:** Канон — **Defect (подтверждённое недопустимое несоответствие)**

> **Уточнение (Session 008, ADR-017).** `Defect — подтверждённый дефект` создаётся
> **только после инженерной оценки** и явного подтверждения ОГС и ОТК. Отделён от
> [[#Quality Finding|Quality Finding]] (обнаруженный признак) и `Inspection Result`
> (технический результат): `Inspection Result ≠ Quality Finding ≠ Defect`. Ролевое
> разделение Session 007 (лаборатория фиксирует индикацию → ОТК подтверждает → ОГС
> решает) сохраняется как вход в оценку. Полное определение жизненного цикла и правил
> — Раздел 10 (Session 008).

### Определение

Подтверждённое недопустимое несоответствие сварного соединения, признанное таковым
**после инженерной оценки** (Engineering Evaluation) и подтверждения ОГС и ОТК.
Владелец инженерной сущности — ОГС; ОТК — обязательный участник подтверждения,
проверки и контроля закрытия. Связь с [[#Quality Finding|Quality Finding]] —
многие-ко-многим. Содержит тип (из расширяемого справочника), описание,
[[#Defect Localization|локализацию]], размеры, нормативные классификаторы и
[[#Defect Severity|критичность]].

Жизненный цикл (ADR-017): `DRAFT — черновик → CONFIRMED — подтверждён →
REPAIR_REQUIRED — требуется ремонт → REINSPECTION_REQUIRED — требуется повторный
контроль → CLOSURE_PENDING — ожидает закрытия → CLOSED_AFTER_REPAIR — закрыт после
ремонта / CLOSED_AS_ACCEPTABLE — закрыт как допустимый`; плюс `REJECTED — признан
ошибочно созданным` (дефект не подтвердился) и `CANCELLED — отменён по процессной или
управленческой причине`. `CONFIRMED` — только после подтверждений ОГС и ОТК;
отменить подтверждённый Defect может только главный сварщик с обоснованием и
сохранением истории.

> Ранние статусы `OPEN` / `IN_REPAIR` / `CLOSED` (черновик ADR-009) **замещены**
> жизненным циклом ADR-017.

### Владелец

Quality (`quality`) — ОГС (владелец инженерной сущности) / ОТК (подтверждение,
проверка, контроль закрытия)

### Используется

Production, Documents.

### Не является

- [[#Quality Finding|Quality Finding]] (обнаруженным признаком до оценки);
- `Inspection Result` (техническим результатом метода);
- [[#Repair|Repair]] / RepairOperation;
- комментарием без статуса в системе;
- Inspection.

### Связанные ADR

ADR-008, ADR-009 (черновик статусов — замещён), ADR-015, ADR-017

## Repair

**Статус:** Канон (проектный, Session 008 / ADR-017; реализация — Task 9H — 9I)

### Определение

Отдельный процесс устранения одного или нескольких [[#Defect|Defect]]. Связь
`Defect ↔ Repair` — многие-ко-многим (один Defect может иметь несколько
последовательных [[#Repair Attempt|попыток]], один Repair может устранять несколько
Defect в одной операции). Выполненный Repair **не** означает автоматического
устранения Defect. Мастер создаёт заявку, ОГС оформляет и утверждает
[[#Repair Plan|план ремонта]], ОТК согласовывает.

Жизненный цикл (ADR-017): `DRAFT — черновик → PLANNED — запланирован →
APPROVED — утверждён → IN_PROGRESS — выполняется → PAUSED — приостановлен →
REWORK_REQUIRED — требуется доработка → PERFORMED — физически выполнен →
VERIFICATION_PENDING — ожидает проверки ОГС и ОТК → COMPLETED — завершён и
подтверждён`; плюс `REJECTED — ремонтная попытка отклонена` и `CANCELLED — отменён`.
`RESUMED — возобновлён` фиксируется как **событие**, а не отдельное длительное
состояние.

### Владелец

Production (мастер — заявка и выполнение) / Quality — ОГС (план, техническая
корректность) / ОТК (согласование, качество)

### Используется

Production, NDT, Documents.

### Не является

- новым Joint;
- [[#Reinspection|Reinspection]] (повторным контролем);
- автоматическим закрытием [[#Defect|Defect]].

### Связанные ADR

ADR-017

## Reinspection

**Статус:** Канон (проектный, Session 008 / ADR-017; реализация — Task 9J)

Production, Documents.

### Не является

## LAB_CONFIRMED / VERIFIED / NOT_EVALUATED (терминология)

**Статус:** Канон (реализовано, Task 9C)

- **`LAB_CONFIRMED`** — терминальный статус `MethodExecution`: подтверждение
  лабораторного результата либо внутренняя регистрация внешнего лабораторного
  документа. **НЕ является решением ОТК.**
- **`VERIFIED`** — зарезервирован для будущего этапа проверки ОТК; в Task 9C **не
  реализуется** и в статусах выполнения отсутствует.
- **`NOT_EVALUATED`** — оценка результата ещё не сформирована (значение оценки).
- **`CONTROL_NOT_PERFORMED`** — тип отмены выполнения: контроль не выполнен. Это
  **другое** понятие, чем `NOT_EVALUATED`; невыполненный контроль отражается lifecycle
  и `cancellation_type=CONTROL_NOT_PERFORMED`, а не значением оценки.

ADR-015

## Quality Decision

**Статус:** Канон

### Определение

Решение ОГС, ОТК или главного сварщика по результату инженерной оценки
[[#Quality Finding|Quality Finding]]. Решения ОГС и ОТК фиксируются раздельно.
Итоговые значения: `ACCEPT — принять`, `REPAIR_REQUIRED — требуется ремонт`,
`REINSPECTION_REQUIRED — требуется повторный контроль`, `REJECT — окончательно
отклонить`. Для каждого решения (в т.ч. `ACCEPT`) обязательны нормативный документ,
пункт/критерий приёмки, текстовое обоснование, автор, дата и время. После фиксации
решение не редактируется — только новая версия с обязательной причиной; старая
версия остаётся в истории. Принимается **отдельно по каждому** Finding.

### Владелец

Quality — ОГС / ОТК; при разногласии — главный сварщик

### Не является

- `Inspection Result`;
- редактируемым полем статуса;
- итоговым решением по Inspection (это [[#Final Decision|Final Decision]]).

### Связанные ADR

ADR-017

---

## Final Decision

**Статус:** Канон

### Определение

Итоговое решение. По каждому Finding итог принимается решением ОГС/ОТК, при
разногласии — `Chief Welder Review` с обязательным обоснованием. Итог по Inspection
рассчитывается автоматически по самому строгому активному решению
(`REJECT > REPAIR_REQUIRED > REINSPECTION_REQUIRED > ACCEPT`). Главный сварщик может
выполнить override рассчитанного итога с обоснованием; автоматически рассчитанный
итог сохраняется отдельно от изменённого. Отменить итоговое решение может только
главный сварщик.

### Владелец

Quality — ОГС/ОТК; главный сварщик (override/отмена)

### Не является

- отдельным решением по одному Finding ([[#Quality Decision|Quality Decision]]);
- вручную перезаписываемым значением без сохранения расчёта.

### Связанные ADR

ADR-017

## Recurring Defect

**Статус:** Канон

### Определение

Повторяющийся дефект. Повторяемость определяется настраиваемым версионируемым
правилом по совокупности признаков (тип дефекта, сварщик, WPS, материал, диаметр,
толщина, участок, проект, период). ОГС формирует правило, главный сварщик утверждает.
Система автоматически выявляет возможную повторяемость; ОГС подтверждает или
отклоняет. При выявлении уведомляются ОГС, ОТК и главный сварщик.

### Владелец

Quality — ОГС (правило и подтверждение) / главный сварщик (утверждение правила)

### Не является

- жёстко зашитым в код порогом;

## Causal Link

**Статус:** Канон

### Определение

Причинная связь [[#Defect|Defect]] с `WeldOperation`. Прямая связь дефекта со
сварщиком **не** создаётся — связь строится как `Defect → WeldOperation → Welder`.
Отдельное инженерное решение с уровнем уверенности `POSSIBLE — возможно`,
`PROBABLE — вероятно`, `CONFIRMED — подтверждено`. ОГС устанавливает/меняет уровень,
ОТК подтверждает достаточность доказательств; история — по версиям, уровни можно
повышать и понижать. `POSSIBLE`/`PROBABLE` — аналитические сигналы; для персональной
ответственности используется только `CONFIRMED`.

### Владелец

Quality — ОГС (уровень) / ОТК (достаточность доказательств)

### Не является

- прямой связью дефекта со сварщиком;
- основанием персональной ответственности при уровнях `POSSIBLE`/`PROBABLE`.

### Связанные ADR

ADR-017

## Repair Attempt

**Статус:** Канон

### Определение

### Владелец

## Repair Plan

**Статус:** Канон

### Определение

Утверждённый план [[#Repair|ремонта]]. Структурирован: связанные [[#Defect|Defect]],
[[#Repair Zone|ремонтная зона]], технология, WPS, способ выборки, требования к
сварщикам, материалы, методы и объём повторного контроля, нормативное основание. Для
сварочного Repair WPS обязателен (исключение — по обоснованию главного сварщика); для
несварочного не требуется. После утверждения план неизменяем — изменения только новой
версией с причиной, повторным утверждением ОГС и согласованием ОТК.

### Владелец

Quality — ОГС (оформление и утверждение) / ОТК (согласование)

### Не является

- фактом выполнения ремонта;
- редактируемым после утверждения документом.

## Repair Zone

**Статус:** Канон

### Определение

Ремонтная зона. Система рассчитывает пересечение ремонтных зон; ОГС определяет,
считать ли участки одной зоной, ОТК подтверждает. Сохраняются координаты, процент
пересечения, решение, обоснование, авторы, дата и время. Учитывается в лимите
`Repair Zone Count`.

### Владелец

Quality — ОГС (определение зоны) / ОТК (подтверждение)

### Не является

- всем [[#Joint|Joint]] целиком;
- [[#Defect Localization|локализацией отдельного дефекта]].

ADR-017

## Repair Deviation

**Статус:** Канон

### Определение

Отклонение от [[#Repair Plan|плана ремонта]], фиксируется отдельно. Уровни:
`MINOR DEVIATION — незначительное отклонение`, `MAJOR DEVIATION — существенное
отклонение`. ОГС определяет уровень, ОТК подтверждает. При `MAJOR DEVIATION` работы
приостанавливаются и создаётся новая версия плана (утверждение ОГС, согласование
ОТК); при `MINOR DEVIATION` новая версия плана не требуется. Все отклонения
учитываются при итоговой оценке ремонта.

### Владелец

Quality — ОГС (уровень) / ОТК (подтверждение)

### Не является

- изменением плана без фиксации;
- [[#Repair Conclusion|итоговым заключением по ремонту]].

### Связанные ADR

ADR-017

## Repair Conclusion

**Статус:** Канон

### Определение

Итоговое заключение по [[#Repair|ремонту]], формируется после его завершения. Система
автоматически собирает фактические данные; ОГС оформляет техническое заключение, ОТК
согласовывает полноту и качество; при разногласии решает главный сварщик.
Окончательное заключение неизменяемо — исправление только новой версией (оформляет
ОГС, повторно согласовывает ОТК).

### Владелец

Quality — ОГС (оформление) / ОТК (согласование)

### Не является

- [[#Repair Deviation|отклонением от плана]];
- редактируемым после выпуска документом.

## Quality Document

**Статус:** Канон

### Определение

Документ качества — единая сущность, связываемая одновременно с `Inspection`,
[[#Quality Finding|Quality Finding]], [[#Defect|Defect]], [[#Repair|Repair]],
[[#Reinspection|Reinspection]] и другими объектами качества; один файл не дублируется
для каждой связи. Категории: `WORKING — рабочий материал`, `EVIDENCE —
подтверждающий материал`, `OFFICIAL — официальный документ` (тип и статус хранятся
раздельно). Жизненный цикл: `DRAFT — черновик → UNDER_REVIEW — на проверке →
APPROVED — утверждён → ISSUED — выпущен → SUPERSEDED — заменён новой версией /
CANCELLED — отменён`. Версионируется: файл выпущенной версии не перезаписывается.
Обязательны подразделение-владелец, ответственное лицо, автор, источник; схема
утверждения настраивается по типу; `ISSUED` возможен только после её прохождения,
выпущенный документ неизменяем. Для каждого файла хранится контрольная сумма (при
совпадении новая физическая копия не создаётся — создаётся новая связь).

### Владелец

Documents — подразделение-владелец документа (лаборатория / ОГС / ОТК по типу)

### Не является

- отдельной копией файла на каждую связь;
- официальным заключением НК как единственным типом (`InspectionReport` /
  `LaboratoryConclusion` — частные случаи официальных документов).

### Связанные ADR

ADR-017

## Quality Document Registry

**Статус:** Канон

### Определение

Единый реестр [[#Quality Document|документов качества]] по проекту, `Joint`,
`Inspection`, [[#Defect|Defect]], [[#Repair|Repair]], [[#Reinspection|Reinspection]].

Documents / Reporting

## Document Authenticity Check

**Статус:** Канон

### Определение

Проверка подлинности документа. Официальный PDF-реестр поддерживает электронную
подпись или электронное утверждение, контрольную сумму, отметку подлинности, дату
формирования, идентификатор версии данных и QR-код. QR-код открывает страницу
проверки подлинности; публично доступны только базовые сведения (статус, номер,
версия, дата выпуска, организация, наличие подписи, результат проверки контрольной
суммы, должность и сокращённое имя подписанта). Полные данные и сам PDF — только при
наличии прав. **Реализация проверки подлинности и публичный API в объём Session 008
не входят.**

### Владелец

Documents

### Не является

- реализованным сервисом/публичным API (открыто, вне канона);
- заменой электронной подписи как таковой.

### Связанные ADR

ADR-017
